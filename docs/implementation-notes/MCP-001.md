- 状态：`READY_FOR_TEST`
- 实现范围：标准 OAuth Protected Resource + Authorization Server discovery、CIMD 优先/DCR 兼容、Authorization Code + PKCE `S256`、资源受众绑定、stateless Streamable HTTP `/mcp`，以及只读 `find_applications` 工具。

## TEST_FAILED 回流修复

- 根因：DCR 注册 view 直接挂在 MCP 自定义 URL 下，未注册 OAuth Toolkit 预期的 `oauth2_provider` URL namespace。DOT 在创建 Application 和注册访问 token 后构造 RFC 7591 响应时执行 `reverse("oauth2_provider:dcr-register-management", ...)`，触发 `NoReverseMatch: 'oauth2_provider' is not a registered namespace`，最终公开响应为 500。
- 修复：新增带 `oauth2_provider` namespace 的 DCR URLconf，挂载 `/oauth/register` 和 `/oauth/register/<client_id>` 到 DOT 官方注册/管理 view；保留 DOT 的 JSON 解析、权限、Application 校验、注册 token 和响应构造逻辑。
- 结果：标准 JSON DCR 请求返回 `201 application/json`，包含 `client_id`、注册访问 token 和 `registration_client_uri`；`redirect_uris` 精确保存并原样返回，例如 `https://client.example.test/oauth/callback`。异常不再因 URL namespace 配置错误泄露 traceback。
- 附带修复：OAuth 登录 HTML 表单增加显式 `action="/oauth/login"`，避免客户端按默认 action 将登录表单错误 POST 到 `/oauth/authorize`。

## 协议与 SDK

- Python MCP SDK：`mcp==2.3.0`，使用官方 v2 `MCPServer.streamable_http_app`。
- 主协议路径：`2026-07-28`，现代请求不要求 `initialize` 或 `Mcp-Session-Id`。
- 兼容路径：保留 SDK 的 `2025-11-25` `initialize`/legacy handshake 处理；兼容路径不成为现代请求的前置条件。
- HTTP 传输：`stateless_http=True`、JSON response，启用 DNS rebinding protection，并按环境配置 allowed hosts/origins。

## OAuth 配置

- Django OAuth Toolkit：`django-oauth-toolkit==3.4.1`。
- Authorization Server Metadata：`/.well-known/oauth-authorization-server`。
- Protected Resource Metadata：`/.well-known/oauth-protected-resource/mcp`。
- 授权端点：`/oauth/authorize`；Token 端点：`/oauth/token`。
- `CIMD_ENABLED=True`，以 HTTPS CIMD URL 作为优先 `client_id`；`DCR_ENABLED=True` 仅用于旧客户端兼容，端点为 `/oauth/register`。
- 授权码流程强制 `response_type=code`、`code_challenge_method=S256`、精确 `redirect_uri`、`state`、`resource=<MCP_RESOURCE_URI>` 和最小 scope `applications:read`。
- Access Token 使用 DOT 存储的 token checksum 校验，并要求资源列表严格等于配置的 MCP resource URI；Web JWT 不可作为 MCP token。
- 发行方、资源 URI、MCP endpoint、allowed origins/hosts 均可通过 `MCP_AUTHORIZATION_ISSUER`、`MCP_RESOURCE_URI`、`MCP_ENDPOINT`、`MCP_ALLOWED_ORIGINS`、`MCP_ALLOWED_HOSTS` 配置。
- OAuth 授权页使用现有 Django session 登录边界；资源请求本身不依赖进程内协议 session。

## 工具与数据隔离

- `tools/list` 只暴露 `find_applications`，标记为只读、非破坏、幂等。
- 工具查询用户从已验证 OAuth token 的 subject 获取，忽略并拒绝 `user_id` 等越权参数；查询使用 `JobApplicationSerializer` 的 APP-012 公司聚合结构。
- 支持应用 ID、公司名、岗位名、全文搜索、状态/阶段筛选和分页；正常结果同时返回可读 `content` 与 `structuredContent`。

## ASGI、进程入口与迁移

- ASGI 入口：`uvicorn backend.config.asgi:application`（从仓库根目录启动）。
- `backend.config.asgi` 将 `/mcp` 和其 Protected Resource Metadata 路由到官方 SDK app，其余 OAuth/Django 路由交给 Django ASGI app。
- 未新增业务迁移；启用 `oauth2_provider` 后需执行 Django OAuth Toolkit 内置迁移 `0001`–`0022`。隔离 PostgreSQL 数据库已完成迁移验证。

## 已知限制与阻塞项

- 成功 OAuth 联调和跨用户查询用例需要外部测试环境提供 CIMD 文档、用户登录会话和测试 token，因此本地对应测试被跳过。
- 当前回流测试的 DCR 失败已修复。剩余 6 个成功路径错误来自测试夹具的认证边界：Web JWT 登录不会写入 Django session，而 `/oauth/authorize` 需要浏览器 session；本实现不把 Web JWT 伪装成 OAuth session，也未修改测试或既有 Web 登录契约。
- DCR 保留为兼容能力；推荐客户端优先使用 CIMD。CIMD 文档必须由可访问的 HTTPS URL 提供，且 `redirect_uris` 必须包含请求中的精确 URI。
