## 业务规则与公开契约

- 部署环境按分钟调用公开管理命令 `python manage.py send_daily_summaries`；命令读取服务器当前时间并对到期用户处理。平台发信账号和连接参数只在应用服务端配置，经 SMTP 发信，不在用户设置 API 中暴露凭据；无需在应用服务器安装完整自建 SMTP 邮件服务器。实现说明须给出服务器定时调用方式、SMTP 配置、监控/故障排查方法。
- 邮件日界与设置时间均按固定 `Asia/Shanghai`。用户在指定分钟已启用且邮箱已验证时符合发送条件；命令延迟运行可在同一北京时间日期内补执行。用户在当天指定时间之后才首次开启或修改发送时间，不追发当天，次日生效。
- 当日安排是北京时间 `[当天 00:00, 次日 00:00)` 内相交的全部本人六阶段事件，包括跨日片段；按开始时间排序。邮件显示北京日期/时区、公司、岗位、阶段、开始、结束；已启用且地址已验证的用户当天零安排时仍发送邮件，正文包含“今日无安排”。
- 对每名用户每个北京日期有唯一发送记录；并发命令不能重复取得同一发送权。状态至少区分待发送、发送中、已被 SMTP 服务器接受、可重试的明确失败、终态失败和结果不确定；重复执行时已接受项不再发。
- `GET /api/v1/notification-settings/` 中的只读 `last_delivery` 为 `null`（尚无发送记录）或 `{ "date": "YYYY-MM-DD", "status": "pending" | "sending" | "accepted" | "failed_retryable" | "failed" | "unknown" }`；日期是北京时间日期。`unknown` 如实显示为结果不确定，不称为发送成功；`failed_retryable` 仅在同日仍可重试时使用，达到尝试上限或过日后状态为终态 `failed`。
- 只有 SMTP 明确拒绝且确认服务器**未接受**时，才可重试；同一北京日期最多重试 3 次（含首次发送总计最多 4 次），每次重试至少间隔 5 分钟，且须在当日 `23:59:59` 前执行。重试次数用尽或日期边界到达后记为终态 `failed`，不再发送旧日邮件。每次重试前重新计算当天安排。连接超时、提交时中断等结果不确定记为 `unknown`，不自动重试。`accepted` 仅表示 SMTP 服务器接受，不承诺收件箱最终投递。
- 日志和持久记录可存用户、日期、状态、尝试次数、脱敏收件地址、SMTP 投递 ID（如有）和故障类别，不存 SMTP 密码、验证令牌、邮件正文或完整敏感日程。

## 输入、输出与错误行为

- 输入：通知设置、已验证收件地址、日历事件和服务器当前时间；管理命令成功结束输出聚合计数，错误退出/日志可区分 SMTP 配置缺失与连接或发送故障。
- 邮件服务未配置时不得把记录标成 `accepted`；单用户发送失败不能阻止其他用户处理。关闭设置、未验证、信息缺失、非到期均不发送。
- 用户删除投递或清空阶段后，尚未发送的当日汇总不能包含该安排。

## 验收标准

- [x] 到期的启用用户收到符合当日日期窗口的完整有序摘要；未到期、关闭、未验证及跨用户数据不发送。
- [x] 跨午夜事件仅按与北京时间当天相交规则纳入，邮件时间/日期/时区正确；零安排也发送且正文包含“今日无安排”。
- [x] 同日重复调用和并发调用最多形成一次 SMTP 接受记录；延迟运行同日补执行，次日不补发旧日。
- [x] SMTP 服务器明确拒绝且确认未接受时，同一北京时间日期最多重试 3 次（总计最多 4 次），间隔至少 5 分钟；次数耗尽或跨日后为终态 `failed`。超时等不确定结果保留 `unknown` 且不自动重试；SMTP 配置缺失不伪报成功。
- [x] 日志和公开错误不包含凭据、验证令牌或邮件正文；发信故障不阻塞其他用户。

## 风险与测试边界

- 外部 SMTP 在超时后是否已接受无法由本系统确定；测试只验证发送权、状态转移和不确定时停止自动重试，不宣称绝对 exactly-once 或收件箱送达。
- 测试使用测试进程时钟控制与邮件服务替身，从管理命令、邮件后端及 `GET /api/v1/notification-settings/` 的 `last_delivery` 观察行为，不阅读实现目录，也不增加生产时钟 API。优先使用现有测试框架时钟控制；若需新增测试依赖或锁文件变更，先由项目管理 Agent 排定测试配置阶段，由测试 Agent 单独修改并验证后再进入实现阶段。
- 正式部署需外部定时器每分钟触发；实施说明必须覆盖进程重启、重复触发和监控。
