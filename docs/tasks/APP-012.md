# APP-012 全局公司库与用户岗位进度关联

- 状态：`DONE`
- 用户价值：公司招聘网站只维护一份并可被所有用户复用；每个用户在自己的公司折叠菜单下管理多个岗位进度，新增岗位不再重复绑定公司网站。
- 范围：全局 `Company` 模型与目录 API；`JobApplication` 到全局公司的关系；用户私有岗位聚合和全局元数据权限；存量迁移与旧 API 兼容；公司选择器、岗位折叠列表和新增/编辑表单；应用、共享、日历、邮件相邻回归。
- 非范围：跨用户共同编辑岗位；公司删除/审核流；APP-011 状态模型重做；日历/邮件新阶段；招聘网站抓取或外部同步；像素级视觉重设计。
- 依赖：`APP-009`、`APP-011`、`WEB-APP-006`、`SHARE-001`，以及现有应用模型/序列化/列表表单契约。系统设计方案第 6、8–11、13、17 节中旧的单用户公司名/岗位链接设计以本任务契约为准。
- 产品契约：`docs/requirements/APP-012.md`
- 允许修改范围：项目管理 Agent 仅 `docs/requirements/`、`docs/tasks/`、`docs/acceptance/`；测试 Agent 仅 `backend/tests/`、`frontend/tests/`、`tests/e2e/`、`docs/test-reports/`；功能实现 Agent 仅 `backend/apps/`、`backend/config/`、`backend/manage.py`、`frontend/src/`、`docs/implementation-notes/`。本任务创建阶段不修改生产代码、测试或实现说明。

## 现状缺口

- `JobApplication` 的 `company_name` 只在单个用户内唯一，无法表达跨用户复用的公司实体。
- `application_url` 同时存在于旧顶层/岗位模型，前端每个岗位重复填写，无法保证公司网站一致。
- `ApplicationsView.vue` 的公司建议只读取当前用户投递；`ApplicationForm.vue` 使用自由文本公司名，没有 `company_id` 选择和全局公司创建竞态处理。
- 当前列表已有公司折叠和多岗位读取基础，但编辑入口、公司网站展示和新增岗位仍与用户私有聚合耦合，必须补成“全局公司 + 私有岗位”的契约。

## 目标数据模型与迁移交付

实现 Agent 必须交付：

1. `Company`（或等价明确命名的全局公司模型）：`company_name`、服务端生成且全局唯一的 `normalized_name`、可空 `recruitment_url`、`created_at`、`updated_at`；不得有岗位/状态/备注/面试等用户私有字段。
2. `JobApplication.company` 非空外键；`user + company` 唯一；保留 APP-009 的 `positions`、`shared_stages`、`interviews` 子关系和最后岗位保护。旧 `company_name` 仅作为兼容投影或迁移过渡字段，不能与 `Company` 形成两个可写来源。
3. 新嵌套岗位不再写 `application_url`；旧列如为兼容保留，必须只读并在实现说明中标明生命周期。旧 flat 响应继续能得到公司招聘网站。
4. 数据迁移跨所有用户按规范化名称合并公司，保留每个用户的独立投递聚合和全部岗位/流程数据。旧链接按固定顺序选择公司 URL，保留旧列，报告合并数和 URL 冲突数；非空数据逆迁移/降级需有保护。
5. 迁移后模型检查、唯一约束、索引和 PostgreSQL 存量数据验证均有实现说明，不以 SQLite 空库通过代替迁移证据。

## 公开 API / UI 实现契约

以 `docs/requirements/APP-012.md` 为唯一细节来源，交付至少包括：

- `GET/POST /api/v1/companies/` 与 `GET/PATCH /api/v1/companies/{id}/`；公司目录分页、搜索、规范化重名 `409 COMPANY_EXISTS`、全局元数据读写和字段错误。
- `GET/POST/PATCH /api/v1/applications/` 兼容 APP-009，新增 `company_id`/`company`/`recruitment_url` 投影；同一用户追加岗位复用原聚合，跨用户只共享公司元数据不共享投递。
- 岗位/面试子资源的父资源和用户双重隔离；所有越权目标统一 `404`，失败写入原子。
- 前端公司搜索/选择/新建、共享网站一次展示、多个岗位折叠与独立编辑、已有公司新增岗位、409 重名复用、加载/错误/未保存状态。
- APP-011 八值状态及 `current_stage`、APP-009 多岗位流程、SHARE-001 共享白名单、日历和邮件的兼容回归。

## 验收标准

- [x] 公司全局唯一、目录可跨用户读取、重复创建不增行且返回明确 `COMPANY_EXISTS`。
- [x] 公司公开元数据与用户投递数据隔离；用户 A/B 复用同一公司时只看到各自岗位，跨用户私有资源为 `404`。
- [x] 同一用户新增同公司岗位复用同一 `JobApplication`/`company_id`，不重复绑定招聘网站；公司的 URL 更新对所有用户一致可见。
- [x] API 拒绝新岗位写入 `application_url`，保留必要 flat 兼容投影；状态、备注、流程和招聘网站互不串改。
- [x] 公司折叠菜单能查看并编辑当前用户的多个岗位；列表刷新、搜索、分页、详情回填和失败保存均符合公开契约。
- [x] 存量迁移保留所有用户岗位及流程，跨用户仅合并公司实体；合并数、URL 选择/冲突、异常和逆迁移保护有证据。
- [x] 既有共享、日历、邮件和 APP-011 相关公开行为回归通过，不泄露私有字段。
- [x] TDD 顺序严格为 `PLANNED → TEST_WRITING → RED_CONFIRMED → IMPLEMENTING → READY_FOR_TEST → TEST_PASSED → ACCEPTING → DONE`；失败按工作流回流，不得跳过独立复测。

## 风险与黑盒测试边界

- 名称规范化、并发创建、跨用户同名公司和 URL 冲突是迁移与唯一性高风险点。
- 全局公司读权限不能扩大到用户投递读权限；测试必须验证目录可见但应用不可见。
- 兼容消费者仍依赖旧字段；测试不得通过删除旧断言或放宽共享白名单来“通过”。
- 测试 Agent 先写黑盒测试并提交 `docs/test-reports/APP-012-red.md`，只能改测试目录和报告目录，不得读取/修改生产实现目录。
- 功能实现 Agent 只修生产实现、迁移和实现说明；收到 `RED_CONFIRMED` 后开始，测试目录视为只读，完成后提交 `docs/implementation-notes/APP-012.md` 和 `READY_FOR_TEST`。
- 测试 Agent 独立复测并提交 `APP-012-passed.md` 或 `TEST_FAILED`，实现自测不能代替复测；项目管理 Agent 只有收到 `TEST_PASSED` 后才能创建验收记录并设置 `DONE`。
