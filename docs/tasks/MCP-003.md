# MCP-003 MCP 写操作安全闭环

- 状态：`DONE`
- 用户价值：AI 可以先展示待写入的明确差异，用户确认后安全应用；重复消息、过期提案和并发修改不会造成重复或覆盖，并可追溯每次写入。
- 范围：`preview_application_change`、`apply_application_change`、明确确认、短时效持久化 proposal、用户/客户端/resource 绑定、幂等键、冲突检测、审计日志和公开结构化结果。
- 非范围：邮箱/聊天读取、大模型抽取、删除、任意 REST/SQL、stdio、Resources、Prompts、SSE、OAuth 服务重构和审计后台 UI。
- 依赖：`MCP-002` 必须已完成并提供稳定的 `create_application`、`upsert_application_stage` 语义化业务能力；同时依赖 `MCP-001`、APP-011、APP-012。
- 允许修改范围：项目管理 Agent 仅 `docs/requirements/`、`docs/tasks/`、`docs/acceptance/`；测试 Agent 仅 `backend/tests/`、`docs/test-reports/`；功能实现 Agent 仅 `backend/apps/`、`backend/config/`、`backend/manage.py`、后端运行时依赖、数据库迁移、`docs/implementation-notes/`。

## 业务规则与公开契约

- preview/apply 都要求 `applications:write`，都继承 MCP-001 的 Bearer、资源受众、用户隔离和无状态 HTTP 约束。
- `preview_application_change` 只接受 MCP-002 的语义化 operation 和结构化 change，生成数据库 proposal；返回 before/after、警告、`proposal_id`、`expires_at` 和 `confirmation_required=true`，不写业务数据。
- `apply_application_change` 只接受属于当前用户/客户端/resource、未过期未消费的 proposal，并要求 `confirm: true`；应用前重新检查原状态指纹。
- proposal、幂等状态和审计不能放进进程内存；服务重启和多副本请求必须保持一致。
- 同一幂等键重复请求返回原结果，不重复写入；相同键不同参数指纹返回冲突。并发改变目标时返回 `CONFLICT`，不覆盖新数据。
- 审计记录操作上下文和脱敏前后摘要；不得记录凭据、授权码、密码、完整邮件或 SQL。

## 输入、输出与错误行为

- `preview_application_change` 输入：`operation`、当前用户可定位的 `target`、MCP-002 的结构化 `change`、可选 `idempotency_key`；输出 proposal 元数据、差异、警告、短时效和确认要求。
- `apply_application_change` 输入：`proposal_id`、布尔 `confirm=true`、可选幂等键；成功输出 `status=applied`、应用结果、`audit_id` 和 replay 标记。
- 无 Token/无效 Token：`401`；无写 scope：`403 insufficient_scope`。
- proposal 不存在/跨用户/跨客户端/resource：不可枚举错误；过期/已应用/已撤销、确认错误、冲突和幂等参数冲突分别返回稳定错误码，不执行错误写入。
- 所有业务、审计或事务失败都必须可观察为失败，不能留下部分数据或无审计成功。

## 验收标准

- [x] preview 只产生持久化 proposal 和必要审计，不改变投递、岗位或流程数据；输出公开 before/after 和短时效。
- [x] apply 必须显式 `confirm=true`，并校验 proposal 所属主体、scope、resource、过期和一次性状态。
- [x] 目标变化返回 `CONFLICT`，不覆盖；同幂等键重放不重复写入，参数不一致拒绝。
- [x] 服务重启/无 session/多副本后 proposal 仍可正确应用或拒绝。
- [x] 审计覆盖成功、失败、过期、冲突和重放，且无敏感原文；审计失败不产生无记录写入。
