# MAIL-001 RED_CONFIRMED 通知设置与收件地址验证 API

- 测试角色：测试 Agent
- 环境：Windows；Python 3.11.13；uv 0.7.21；本机 PostgreSQL，使用独立测试数据库 `postgres_mail001_red3_test`、`postgres_mail001_red4_test`、`postgres_mail001_red5_test`，以及认证前置探针库 `postgres_mail001_probe_test`。`SECRET_KEY` 为进程级临时测试值，未记录其内容；未配置真实 SMTP，也未触发真实外发。
- 命令：`DATABASE_URL=<本机独立测试库 DSN> SECRET_KEY=<临时测试值> uv run pytest tests/test_mail_001.py --tb=no -q`
- 通过 / 失败：三次完整运行均为 0 / 9；每次均为 9 failed、0 errors，分别耗时 11.19 秒、11.03 秒和 12.09 秒。
- 公开输入：认证用户调用 `GET/PATCH /api/v1/notification-settings/`，以及 `POST /api/v1/notification-settings/verification/`、`POST /api/v1/notification-settings/verify/`；发送邮件测试只配置 Django locmem 邮件后端或测试专用失败邮件后端。
- 期望行为：通知设置可查询和修改并严格按用户隔离；未经验证不能启用；邮箱验证令牌限时、一次性并绑定用户及当前地址；每小时最多申请 3 次；SMTP 未配置或发送失败时返回可观察错误且不泄露秘密、不误标验证成功。
- 实际行为：既有注册和登录公开 API 分别返回 `201`、`200`，通知设置 GET、验证邮件申请 POST、令牌确认 POST 均返回 `404 text/html`。完整测试的 9 条测试均以断言失败结束（`F`），没有测试收集、数据库建库、认证夹具或其他环境错误；三个独立测试库上的运行得到相同的 9 个失败。由于入口接口缺失，各场景均在首次相关 API 断言处停止，尚不能观察其后续验证/邮件分支的实际响应。
- 是否稳定复现：是。三次完整定向运行均有完全相同的 9 条失败。测试环境使用不同数据库名以避免其他并行任务占用默认测试库。
- 回归结果：未运行相邻回归；既有认证 API 仅作为公开测试流程中的注册/登录前置条件。通知 API 路径返回 404 已证明新增行为缺失。
- 覆盖的验收标准：默认关闭及安全字段；本人 GET/PATCH 和用户隔离；字段格式校验；未认证 401；启用前验证约束；改地址撤销验证；令牌验证、重放拒绝、用户/地址绑定、24 小时过期；每小时三次限流；SMTP 缺失/连接失败不伪报成功、不改变验证状态及不泄漏凭据。
- 未覆盖风险：接口目前返回 404，故验证邮件正文内链接的具体呈现、SMTP 失败分支和错误体细节尚无法到达；这些行为会在实现后由同一测试集独立复测。
- 黑盒声明：未读取或分析生产实现代码。测试只通过注册、登录和公开 HTTP 请求观察行为；邮件后端替身仅用于阻止真实外发。
