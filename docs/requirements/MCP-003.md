# MCP-003 MCP 写操作安全闭环契约

## 目标

在 MCP-002 写工具可用的基础上，建立写操作的安全闭环：AI 先提交结构化变更提案，用户明确确认后才能应用；提案短时效、绑定 OAuth 用户和客户端，应用时进行幂等和冲突检测，并留下可审计记录。服务保持 MCP 标准 OAuth、Streamable HTTP、stateless/no protocol session，不依赖进程内存保存提案状态。

## 范围

1. MCP 工具 `preview_application_change`：根据目标和变更内容生成数据库持久化的 proposal，返回修改前后差异和警告。
2. MCP 工具 `apply_application_change`：仅接受当前用户、当前客户端、未过期且未使用的 proposal，并要求明确确认字段。
3. proposal 短时效、一次性消费、用户/客户端/资源受众绑定。
4. 幂等键：同一用户和操作键重复请求不得重复创建或重复应用；重放行为公开且确定。
5. 冲突检测：预览后目标数据被其他操作改变时拒绝应用，不覆盖新数据。
6. 审计日志：记录用户、客户端、工具、目标、变更前后摘要、结果、请求 ID、时间和失败原因；不记录 Token、授权码、密码或完整敏感原文。
7. 工具白名单、公开 `structuredContent`、标准 scope 和错误行为。

## 非范围

- 邮箱、聊天记录、附件读取，或 MCP 服务端调用大模型抽取信息。
- 删除投递、任意 REST/SQL、通用模型字段 PATCH、修改保存的 `application_status`（除 MCP-002 已定义范围外）。
- stdio、旧 HTTP+SSE、MCP Resources、Prompts、Tasks、服务端主动推送。
- 替换 OAuth Authorization Server、第三方身份源、多因素认证、完整审计后台 UI 和审计数据导出。
- 把 proposal 放在进程内存、客户端本地或不可校验的自由文本中。

## 依赖与允许修改范围

- 依赖：`MCP-002`（必须已通过独立复测并进入 `DONE` 或项目管理明确允许的稳定交接状态）、`MCP-001`、`APP-011`、`APP-012`。
- 项目管理 Agent：仅 `docs/requirements/`、`docs/tasks/`、`docs/acceptance/`。
- 测试 Agent：仅 `backend/tests/`、`docs/test-reports/`。
- 功能实现 Agent：`backend/apps/`、`backend/config/`、`backend/manage.py`、后端运行时依赖、数据库迁移、`docs/implementation-notes/`；不得修改测试、任务单或质量门槛。

## OAuth 与工具白名单

- `preview_application_change` 和 `apply_application_change` 都必须要求 `applications:write`；不得用 `applications:read` 生成或应用写 proposal。
- MCP-001/MCP-002 的 Bearer 校验、资源受众、当前用户隔离和 stateless HTTP 继续有效。
- `tools/list` 必须暴露 MCP-002 的稳定工具和本任务的两个工具：`find_applications`、`create_application`、`upsert_application_stage`、`preview_application_change`、`apply_application_change`；不得暴露 proposal 数据库 CRUD、审计日志查询、REST、SQL、邮箱或任意通用写入工具。
- 每个工具必须有完整 JSON Schema、清晰描述和公开 `structuredContent`；禁止把确认语义隐藏在自然语言提示中。

## Proposal 数据与生命周期

### `preview_application_change`

输入 JSON object：

```json
{
  "operation": "upsert_application_stage",
  "target": {"application_id": 123, "position_id": 456},
  "change": {
    "stage_type": "interview",
    "interview_round": "second",
    "interview_name": "二面",
    "scheduled_at": "2026-10-18T14:00:00+08:00",
    "duration_minutes": 60
  },
  "idempotency_key": "mail-456-stage"
}
```

规则：

- `operation` 只能引用 MCP-002 已定义的语义化新增投递或阶段更新时间；不能提交任意模型字段、REST URL、SQL、`user_id` 或通用 JSON Patch。
- `target` 必须能唯一定位当前用户资源；多匹配、缺失或跨用户目标必须在预览阶段拒绝或要求补充明确目标。
- 服务在事务内读取当前公开状态，校验 MCP-002 的所有业务规则，生成规范化变更和指纹；proposal 必须保存原始状态指纹、用户、客户端、资源受众、申请 scope、创建时间、过期时间、状态和幂等键。
- proposal 默认短时效，建议不超过 10 分钟；具体 TTL 必须配置化并在响应中返回 `expires_at`，过期后不可应用。
- 同一 OAuth 用户/客户端/操作的同一 `idempotency_key` 重复预览必须返回同一个有效 proposal 或明确的已完成结果，不得生成无法区分的多个写意图。

成功 `structuredContent`：

```json
{
  "proposal_id": "prop_123",
  "status": "pending_confirmation",
  "expires_at": "2026-10-11T10:10:00+08:00",
  "target": {"application_id": 123, "position_id": 456},
  "operation": "upsert_application_stage",
  "changes": [
    {"field": "second_interview_time", "from": null, "to": "2026-10-18T06:00:00Z"}
  ],
  "warnings": [],
  "confirmation_required": true
}
```

### `apply_application_change`

输入 JSON object：

```json
{
  "proposal_id": "prop_123",
  "confirm": true,
  "idempotency_key": "mail-456-stage-apply"
}
```

规则：

- `confirm` 必须是 JSON 布尔值 `true`；缺失、`false`、字符串或自然语言替代均不得写入。
- 服务必须验证 proposal 属于当前 OAuth `sub`、当前客户端和 MCP resource，scope 足够，状态为待确认，未过期且未被消费。
- 服务必须在同一事务中重新读取目标和原状态指纹；若目标已被修改、删除、权限变化或 proposal 指纹不再匹配，返回冲突，不覆盖当前数据。
- 成功应用与 proposal 状态更新必须原子完成；重复使用相同 proposal 或幂等键返回先前结果，不重复写入，不重复生成审计成功事件。
- 应用必须调用 MCP-002 的同一语义化业务服务，继续遵循 APP-011/APP-012 的事务、隔离和 `current_stage` 规则。

成功 `structuredContent`：

```json
{
  "proposal_id": "prop_123",
  "status": "applied",
  "idempotent_replay": false,
  "application": {"id": 123, "positions": []},
  "audit_id": "audit_456"
}
```

重复成功请求必须返回 `status: "applied"`、`idempotent_replay: true` 和原应用结果，不能再次改变数据。

## 审计日志公开边界

每次预览和应用至少记录：

```text
audit_id
request_id
user_id/sub
client_id
resource
tool_name
operation
proposal_id
idempotency_key_hash 或安全标识
target resource ids
changed field names
redacted before/after summary
success/failure/conflict/expired/replay
created_at
```

日志中不得保存完整 Access Token、Refresh Token、authorization code、密码、邮箱全文、附件内容、SQL 或内部堆栈。审计数据库写入失败时，应用写入不得假装成功；应按事务/可靠事件语义返回失败并避免形成无审计的成功变更。

## 错误行为

| 情况 | 公开行为 |
|---|---|
| 未认证/Token 无效 | HTTP `401`，带 MCP-001 发现指引 |
| 无 `applications:write` | HTTP `403`，`insufficient_scope` |
| proposal 不存在、属于其他用户/客户端/resource | 统一 `404` 或等价不可枚举错误，不泄露 proposal 存在性 |
| `confirm` 非布尔 `true` | 参数/确认错误，不写入 |
| proposal 过期、已应用、已撤销 | 明确 `PROPOSAL_EXPIRED`/`PROPOSAL_ALREADY_APPLIED`/`PROPOSAL_REVOKED`，不重复写入 |
| 原数据已变化 | `CONFLICT`，返回重新预览提示，不覆盖新数据 |
| 幂等键重放 | 返回原结果并标识 `idempotent_replay=true`；参数指纹不一致则拒绝冲突 |
| 业务校验/事务/审计失败 | `isError=true`，无部分写入，不返回敏感信息 |

## 验收标准

- [ ] 两个新工具要求 `applications:write`，工具白名单只增加语义化 preview/apply，不暴露 proposal CRUD、审计查询、REST、SQL、邮箱或任意 PATCH。
- [ ] `preview_application_change` 能返回当前用户目标的规范化 before/after 差异、警告、proposal ID、短时效和 `confirmation_required=true`；预览不改变业务数据。
- [ ] `apply_application_change` 只有在 proposal 所属用户/客户端/resource、未过期、未消费且 `confirm=true` 时才写入；`confirm=false`、自然语言确认、缺 scope 或跨用户 proposal 均不写入。
- [ ] proposal 在服务重启、多个副本和无 session 请求之间仍可验证；不能依赖进程内存或上一次 HTTP 请求状态。
- [ ] 预览后目标被修改时，应用稳定返回 `CONFLICT`，保留新数据并要求重新预览；不会覆盖其他操作。
- [ ] 相同用户/客户端/操作的相同幂等键不会重复创建或应用；重复成功返回原结果并标识 replay，参数指纹不一致被拒绝。
- [ ] 成功、失败、冲突、过期和重放均有可审计记录；审计不包含 Token、授权码、密码、邮箱全文、SQL 或堆栈；审计失败不会形成无记录成功写入。
- [ ] apply 成功继续遵循 MCP-002、APP-011 和 APP-012 的用户隔离、事务、阶段投影和公开 structuredContent；无 proposal 应用不改变数据。
- [ ] 测试 Agent 先提交稳定 `RED_CONFIRMED`；实现 Agent 只写生产和迁移；测试 Agent 独立复测 `TEST_PASSED` 后才进入项目管理验收。

## 风险与测试边界

- 黑盒测试只能使用公开 OAuth、MCP JSON-RPC、工具结果和公开数据库可观察行为；审计只通过公开测试配置/可观察副作用验证，不读取生产实现。
- 必须覆盖服务重启/无状态、多副本等价请求、短时效、确认布尔值、用户/客户端/resource 绑定、数据冲突、幂等重放、参数指纹冲突、审计失败和事务回滚。
- 测试不得依赖邮箱内容或大模型抽取；直接提交 MCP-002 已定义的结构化变更。
- 如果 `MCP-002` 的工具输出尚未稳定，MCP-003 不得自行改写其契约；应回到项目管理 Agent 更新依赖或拆分兼容任务。
