# CAL-001 日历安排与每日邮件通知需求

- 需求状态：需求契约已确认；七项任务均保持 `PLANNED`，按各自依赖进入 TDD 流程。
- 用户价值：在周、月日历中按一天的时间位置查看六类笔试/面试，并可在指定时刻收到当天安排邮件。
- 基线：扩展《校招进度管理系统-详细设计方案.md》V1.0；V1.0 中“消息提醒、日历同步不包含”对本需求不再适用。既有投递 CRUD、JWT 用户隔离与 UTC 存储规则继续适用。

## 1. 范围与用户流程

1. 登录用户从导航进入“日历”页面，默认定位今天，可切换周/月、上一周期、下一周期、回到今天。
2. 周视图展示周一至周日，每天从 00:00 到 24:00 自上而下排布；月视图按自然月组成日期网格，**每个日期格内也有从上到下的紧凑 24 小时时间轴**。时间轴上的安排落在其开始至结束时段，点击安排显示公司、岗位、阶段、开始、结束、时长，并可进入原投递编辑页。
3. 在现有新增/编辑投递表单中，AI 面、笔试、一面、二面、三面、HR 面各自增加“时长（分钟）”。保存阶段开始时间和时长后成为一条日历安排。
4. 用户在通知设置中配置收件邮箱、是否启用、每天发送的本地时间；到时由服务端发送当日在日历时区内的全部安排摘要。

非范围：外部日历双向同步、邀请或会议链接、短信/站内推送、投递时间本身作为日历事件、任意自定义事件、周期性事件、多人共享、邮件回复处理。

## 2. 六阶段时长契约

| 阶段 | 既有开始字段 | 新增时长字段（整数分钟） |
| --- | --- | --- |
| AI 面 | `ai_interview_time` | `ai_interview_duration_minutes` |
| 笔试 | `written_test_time` | `written_test_duration_minutes` |
| 一面 | `first_interview_time` | `first_interview_duration_minutes` |
| 二面 | `second_interview_time` | `second_interview_duration_minutes` |
| 三面 | `third_interview_time` | `third_interview_duration_minutes` |
| HR 面 | `hr_interview_time` | `hr_interview_duration_minutes` |

- 时长为 1～1440 整数分钟；有开始时间必有时长，无开始时间时长为 `null`。零、负数、小数、字符串及超出上限均返回字段级 `400 VALIDATION_ERROR`。
- 兼容旧数据：迁移时，已填写开始时间且无时长的阶段补 60 分钟；开始时间为空的阶段时长保持 `null`。新设开始时间但未提交对应时长且此前无时长时默认 60 分钟；若该阶段已有自定义时长，单独改开始时间时保留原时长。用户可随后编辑真实时长。
- 清空阶段开始时间时，该阶段时长一同清空；同一请求若同时清空开始时间并提供非空时长则返回字段级 `400`。只改时长不改开始时间时，以当前已保存开始时间校验；无开始时间时不可单独设置时长。PATCH 未涉及的其他阶段不变。
- 创建/详情/列表/更新响应包含六个时长字段，供前端回填；既有 `current_stage` 派生规则不因时长改变。
- 结束时间按开始瞬间加时长计算，跨日不截断或改写原事件。

## 3. 日历查询与时间规则

- 日历与每日邮件统一固定 `Asia/Shanghai`，页面显式标注“北京时间”；邮件按该时区确定“今天”和发送时刻。数据库仍以 UTC 保存，API 继续输出带时区 ISO 8601。现有投递表单按浏览器本地时区显示的行为需在页面上明确区分，避免同一时间在两个页面被误读。
- 独立接口：`GET /api/v1/calendar/events/?start=YYYY-MM-DD&end=YYYY-MM-DD`。`start` 为北京时间内包含的起始日期，`end` 为不包含的结束日期；`start < end`，跨度最多 42 天。返回与此日期窗口有任意交集的本人事件，不能套用投递列表的 100 条分页上限。
- 每条事件公开字段：`application_id`、`company_name`、`position_name`、`stage`（六个阶段的稳定代码）、`start_at`、`end_at`（带时区 ISO）、`duration_minutes`。响应另含 `timezone`、`start`、`end`；按 `start_at`、`application_id`、阶段固定顺序稳定排序。
- 事件与查询窗口只要时间区间相交即返回：事件区间 `[start_at, end_at)`，日期窗口亦为左闭右开。恰好在午夜结束的事件不算入次日；跨午夜事件在所跨的每个日期按该日相交时间段绘制，但详情仍显示原始开始和结束。
- 同一投递记录的六阶段分别成事件；不同安排可重叠，不合并、不覆盖；重叠安排在相同时间位置并列或以可操作的聚合入口展示，能访问每一条详情。
- 未填写阶段开始时间不生成事件；已删除投递不再出现。`offer`、`rejected`、`withdrawn` 等投递状态不自动删除已设定的阶段安排，用户可清空阶段时间来取消。
- 未登录返回 `401`；非法日期、反向区间或跨度超限返回字段级 `400 VALIDATION_ERROR`；不能查询或推断其他用户的安排。查询失败时保留当前视图并提供重试。

## 4. 周/月视图

- 周以周一为首日；月视图展示该自然月覆盖的完整周，可包含邻月日期。两种视图均按显示范围一次获取完整事件；切换或翻页时重新查询对应范围。
- 每日时间轴从 00:00 到 24:00 自上而下；事件的垂直位置由时间决定，长度对应当日在该日期内的时长。月视图采用紧凑时间轴，窄小时段用最小可点击高度和详情承载文字；不能为容纳文字而把事件移到错误时刻。
- 每一天可看出是否有 AI 面/一面/二面/三面/HR 面、是否有笔试；非面试的笔试须与面试区分。无安排的日期呈现明确空状态。
- 当天事件过多时可折叠文字或显示数量，但所有事件仍可经该日入口查看；不可静默丢弃。键盘可进入事件和详情；用文字/形状辅助区分类型，不能仅靠颜色。
- 页面标题、今日标识、事件详情和邮件中的日期时间均按日历时区；跨日显示应能看出续接。查看日历不会修改投递记录。

## 5. 邮件通知契约

- 应用服务端统一配置平台发信账号与 SMTP 主机、端口、认证凭据、加密方式和发件地址，通过 SMTP 发送验证邮件与每日摘要；用户只配置自己的收件邮箱和每日推送时刻。无需在应用服务器安装完整自建 SMTP 邮件服务器。SMTP 凭据仅在服务端配置，绝不由浏览器传输或回显；配置缺失或连接失败时不得伪报发送成功。
- 每个用户一份通知设置：`recipient_email`、`daily_time`（北京时间 `HH:mm`，分钟精度）、`enabled`、`timezone`（固定 `Asia/Shanghai`）。未配置完整资料时 `enabled=false`；用户可关闭或修改设置。
- 为避免把个人日程发送给误填地址，启用新收件地址前需验证该地址。修改地址时旧地址不继续接收，新地址未验证前不发送安排。验证令牌一次性、限时、不可回显；验证和发送失败均不得泄露完整令牌或发信凭据。
- 验证邮件的链接进入 `/notification-settings/verify?token=...`；前端读取后立即从地址栏移除令牌，再调用验证 API，不能把令牌写入长期客户端存储或日志。
- 接口：`GET/PATCH /api/v1/notification-settings/` 查询/修改本人设置；`POST /api/v1/notification-settings/verification/` 向待验证地址发验证邮件；`POST /api/v1/notification-settings/verify/` 消费令牌。公开响应向本人展示收件地址、验证状态及只读 `last_delivery`。`last_delivery` 为 `null`（尚无发送记录）或 `{ "date": "YYYY-MM-DD", "status": "pending" | "sending" | "accepted" | "failed_retryable" | "failed" | "unknown" }`，其中日期为北京时间日期；不展示验证令牌或发信凭据。更新失败给字段级错误。未认证统一 `401`，用户数据严格隔离。
- 已启用通知且收件地址已验证时，每日指定时刻发送**当日安排**，范围为北京时间的 `[当天 00:00, 次日 00:00)`，包含跨入当天的安排。内容含日期、时区、每条安排的公司、岗位、阶段、本地开始和结束时间；重叠安排都列出。当天零安排仍发送一封正文明确包含“今日无安排”的邮件。
- 日常调度按“用户 + 北京日期”建立唯一发送记录，并发工作进程只能有一个取得发送权。记录 `pending`、`sending`、`accepted`、`failed_retryable`、`failed`、`unknown` 等可观察状态；`accepted` 表示 SMTP 服务器已接受，不保证收件人最终收到。已 `accepted` 不再自动发送。SMTP 明确拒绝且确认未接受时，同一北京日期最多重试 3 次（含首次发送总计最多 4 次），每次重试至少间隔 5 分钟，并须在该日 `23:59:59` 前执行；超过次数或日期边界后转为终态 `failed`，不再发送旧日邮件。每次重试前重新计算当日安排，使修改可生效。
- 连接超时、进程在提交邮件时中断等“可能已被 SMTP 服务器接受”的结果记为 `unknown`，**不自动重试**，由管理员查看 SMTP 服务日志或投递 ID 后人工处理；没有可核对依据时保持 `unknown`。这避免系统自己造成可预见的重复邮件，但不承诺端到端恰好送达一次。服务端日志不记录邮件正文、验证令牌或凭据；可记录脱敏邮箱、日期、投递 ID 和结果。
- 发送时间刚好到达时，以发送任务实际执行时的已提交投递数据为准。设置关闭、地址未验证或配置缺失时不发送；用户删除投递后邮件中不再出现该安排。系统发信配置缺失时任务安全失败并可观测告警，不能误标已发送。

## 7. 端到端验收场景

- 用户为同一投递设置笔试和一面不同时段，周/月视图在正确日期、时间位置显示两条；月视图每个日期格从上到下对应 24 小时。
- 23:30 开始、时长 120 分钟的安排在两天日历中各出现对应片段；午夜结束的安排仅属于前一天。
- 同一时间的多个安排都可查看；超过 100 条事件不会因投递列表分页而遗漏；其他用户安排不可见。
- 保存/修改/清空阶段时间或时长后日历随刷新更新；旧阶段时间的默认 60 分钟可见且可编辑。
- 已验证邮箱启用推送后，平台服务端经 SMTP 在指定北京时间发送当日完整安排；零安排邮件正文包含“今日无安排”；重复调度不重复投递；关闭、未验证、SMTP 配置缺失或发送失败分别有可观察结果。

## 8. 已确认决策

1. **发信账号归属**：平台在应用服务端统一配置 SMTP 发信账号和连接参数，经 SMTP 发送验证邮件与每日摘要；用户只配置收件邮箱与推送时间，不配置个人 SMTP 凭据。
2. **日历/邮件时区**：统一固定 `Asia/Shanghai`，日历和设置 UI 标注“北京时间”，每日发送时刻与“今天”的日期边界均以此为准。
3. **空日邮件**：通知已启用且地址已验证时，即使当天没有安排也发送邮件，正文包含“今日无安排”。
