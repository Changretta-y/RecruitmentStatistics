# MCP-002 标准 OAuth MCP 写工具第一期契约

## 目标

在已完成 MCP-001 的 OAuth Resource Server、Streamable HTTP `/mcp` 和 `find_applications` 基础上，增加面向 AI 客户端的最小写入能力：新增投递，以及更新测评、笔试、面试时间。写工具必须通过 OAuth `applications:write` scope、当前用户隔离、语义化输入和现有投递业务服务执行；不得把原始 REST、模型字段、SQL 或任意 PATCH 暴露给 MCP 客户端。

本任务以 APP-011 的八值保存状态/`current_stage` 投影与流程时间规则、APP-012 的公司共享元数据和用户投递/岗位隔离为唯一业务基线，以 MCP-001 已完成的 OAuth 资源受众、协议版本、工具白名单和 `structuredContent` 约定为协议基线。

## 范围

1. OAuth `applications:write` scope 的发现、授权和 Resource Server 校验；保留 `applications:read` 只读能力。
2. MCP 工具 `create_application`：通过公司名称或现有公司标识新增当前用户投递/岗位。
3. MCP 工具 `upsert_application_stage`：新增或更新当前用户投递的测评、笔试和岗位面试时间；支持清空已安排时间。
4. 语义化 JSON Schema、公开 `structuredContent`、可读 `content` 和工具错误结果。
5. 现有 APP-012 公司复用、用户投递隔离、APP-011 流程类型/阶段映射、时间和时长校验、数据库事务与失败原子性。
6. `tools/list` 白名单只增加上述两个工具，并为写工具声明写操作风险；`find_applications` 继续保留且不改变其只读契约。

## 非范围

- `preview_application_change`、`apply_application_change`、明确确认、proposal 短时效、幂等键和审计闭环；这些属于 MCP-003。
- 邮箱、聊天记录、附件读取或 MCP 服务端调用大模型做信息抽取。
- 删除投递、修改公司共享招聘网站、修改保存的 `application_status`、批量写入和任意字段通用 PATCH。
- stdio、旧 HTTP+SSE、MCP Resources、Prompts、Tasks 或服务端主动推送。
- OAuth 管理后台视觉、第三方身份源、多因素认证和 OAuth 授权服务器重构。
- 直接调用原始 REST API、直接访问 SQL/ORM 的公开工具。

## 依赖与允许修改范围

- 依赖：`MCP-001`（状态 `DONE`）、`APP-011`（状态 `DONE`）、`APP-012`（状态 `DONE`）、相关系统设计方案及环境规范。
- 项目管理 Agent：仅 `docs/requirements/`、`docs/tasks/`、`docs/acceptance/`。
- 测试 Agent：仅 `backend/tests/`、`docs/test-reports/`；不得读取或分析生产实现目录。
- 功能实现 Agent：`backend/apps/`、`backend/config/`、`backend/manage.py`、后端运行时依赖、`docs/implementation-notes/`；可新增或修改 MCP 运行配置和数据库迁移，但不得修改测试、任务单或质量门槛。
- 共享配置按 AGENTS.md 归属处理；测试依赖/测试运行配置与生产运行时依赖/配置不得由同一角色越界修改。

## OAuth 与 MCP 公开契约

### Scope

Authorization Server Metadata 和 Protected Resource Metadata 的 `scopes_supported` 必须同时声明：

```json
["applications:read", "applications:write"]
```

授权请求可申请一个或两个 scope，但只能授予用户明确同意的 scope。`applications:write` 不得隐式授予未申请的客户端。Access Token 必须绑定 MCP 资源 URI、当前用户和客户端；没有该 scope 的工具调用必须在 HTTP 层返回 `403` 和 `insufficient_scope`，不能执行写入。

### `/mcp` 与工具白名单

- 继续使用 MCP-001 的 Streamable HTTP、stateless/no protocol session 和 Bearer Token 认证。
- `tools/list` 必须只暴露已实现的 `find_applications`、`create_application`、`upsert_application_stage`，不得暴露原始 REST、SQL、删除或通用更新工具。
- 每个工具必须提供完整 JSON Schema；写工具描述必须说明会创建或修改投递数据。
- 成功工具结果同时提供可读 `content` 和机器可消费的 `structuredContent`；结构必须是公开业务 DTO，不得返回 ORM 对象、内部主键以外的内部字段、Token 或堆栈。

## 业务规则与输入输出

### `create_application`

工具名称：`create_application`。

输入 JSON object：

```json
{
  "company_name": "腾讯",
  "company_id": null,
  "position_name": "后端开发",
  "application_time": "2026-10-11T10:00:00+08:00",
  "application_url": null,
  "notes": "官网投递",
  "application_status": "applied",
  "source": {"type": "email", "id": "mail-123"}
}
```

规则：

- `position_name` 必填且去除首尾空白；`company_id` 与 `company_name` 至少提供一个，二者同时提供时必须指向同一公司。
- 使用 `company_id` 时只能引用公开公司目录中的公司；使用 `company_name` 时按 APP-012 规范化语义查找/创建公司。不得因为用户没有该公司的投递而拒绝复用全局公司元数据。
- 同一 OAuth 用户向同一公司追加岗位时复用现有用户投递聚合；不创建重复公司，不创建重复岗位记录。重复语义如何裁定必须在响应中明确，不能静默覆盖已有私有字段。
- 本任务不允许岗位级 `application_url`；若现有公开模型将招聘 URL 作为公司级共享元数据，MCP 新增投递不得通过该字段修改公司信息。输入存在 `application_url` 时必须明确返回字段校验错误。
- `application_time` 若提供必须是带时区的 ISO 8601 时间；无法确定日期或时区时拒绝写入。`application_status` 只允许 APP-011 八值中的保存状态；默认值为 `applied`。
- `source` 仅作为来源描述，不执行邮箱读取；未知额外字段必须按 schema 拒绝或明确忽略，不能改变用户归属。

成功 `structuredContent` 至少包含：

```json
{
  "application": {
    "id": 123,
    "company_id": 9,
    "company_name": "腾讯",
    "application_status": "applied",
    "current_stage": "applied",
    "positions": []
  },
  "created": true,
  "position_created": true
}
```

真实结果须遵循 APP-012 公司/岗位聚合公开结构，并包含必要的岗位、共享流程和面试公开字段；不能返回其他用户岗位、备注或私有流程。

### `upsert_application_stage`

工具名称：`upsert_application_stage`。

输入 JSON object：

```json
{
  "application_id": 123,
  "position_id": 456,
  "stage_type": "interview",
  "interview_round": "second",
  "interview_name": "二面",
  "scheduled_at": "2026-10-18T14:00:00+08:00",
  "duration_minutes": 60
}
```

规则：

- `application_id` 必填；岗位级流程必须同时有属于当前用户该投递的 `position_id`。缺失、跨用户或不属于投递的目标统一 `404`，不泄露存在性。
- `stage_type` 只能是 `assessment`、`written_test`、`interview`。
- `assessment`、`written_test` 写入 APP-011 对应共享流程；`interview` 写入该岗位的面试流程。面试可使用 `first`、`second`、`third`、`hr`、`other`，自定义名称必须非空且长度受 schema 限制。
- `scheduled_at` 为 `null` 表示清空该阶段时间；清空时长也必须为 `null` 或被服务端同步清空。非空时间必须带时区且格式合法；`duration_minutes` 必须为正整数并在公开上限内。
- 更新一个阶段不得覆盖其他共享类型、其他岗位面试或未提供字段；同一目标的 upsert 结果必须确定。
- 写入后按 APP-011 规则重新计算只读 `current_stage`；不得隐式修改保存的 `application_status`，不得修改其他流程时间、时长或用户私有字段。
- 整个操作必须事务化；任何校验、权限或持久化失败都不得留下部分写入。

成功 `structuredContent` 至少包含：

```json
{
  "application": {"id": 123, "company_id": 9, "positions": []},
  "updated_stage": {
    "type": "interview",
    "round": "second",
    "name": "二面",
    "scheduled_at": "2026-10-18T06:00:00Z",
    "duration_minutes": 60
  },
  "current_stage": "second_interview"
}
```

时间响应允许规范化为 UTC；测试应按带时区瞬时值比较，不要求原输入字符串原样回显。

## 错误行为

| 情况 | 公开行为 |
|---|---|
| 无 Token、无效/过期/受众不匹配 | HTTP `401`，`WWW-Authenticate` 指向 MCP-001 发现文档，不执行工具 |
| Token 无 `applications:write` | HTTP `403`，OAuth `insufficient_scope` |
| 参数缺失、未知枚举、非法时间/时长/额外写字段 | 工具参数错误或 `isError=true`，明确字段，不写入 |
| 目标不存在、跨用户、跨岗位引用 | `404` 语义，不泄露其他用户资源 |
| 公司/岗位冲突或业务唯一性冲突 | 公开业务错误，说明需要查询/确认，不产生部分写入 |
| 数据库/业务异常 | `isError=true`，不返回堆栈、SQL、Token、密码或其他用户数据 |

## 验收标准

- [ ] Authorization Server Metadata、Protected Resource Metadata 和授权同意页公开声明并正确处理 `applications:write`；无该 scope 的写工具请求稳定返回 `403 insufficient_scope`。
- [ ] `tools/list` 只暴露 `find_applications`、`create_application`、`upsert_application_stage`；不暴露 REST、SQL、删除、通用 PATCH、邮箱读取或未实现能力；每个工具有完整 schema 和写/只读语义标记。
- [ ] 已授权用户可通过 `create_application` 创建新公司投递、复用现有公司并追加岗位；结果遵循 APP-012 聚合结构，重复公司/岗位行为确定且不泄露其他用户私有数据。
- [ ] `create_application` 拒绝缺失定位、非法状态、无时区时间、岗位级招聘 URL和伪造用户归属；失败不产生公司、投递或岗位的部分写入。
- [ ] 已授权用户可通过 `upsert_application_stage` 新增/更新测评、笔试、一面、二面、三面、HR 面和自定义面试时间，能够清空时间，并保留其他流程字段/时长。
- [ ] 阶段类型、面试轮次、面试名称、时间和时长均按公开 schema/APP-011 规则校验；更新后 `current_stage` 正确投影且 `application_status` 不被隐式修改。
- [ ] 两个用户使用同一 MCP 工具时只能写入和读取自己的投递/岗位/流程；跨用户 `application_id`、`position_id`、公司私有数据统一阻断，不能通过输入 `user_id` 越权。
- [ ] 写工具事务失败时数据库无部分写入；成功结果同时包含可读 `content` 和公开 `structuredContent`，不包含内部堆栈或敏感凭据。
- [ ] 测试 Agent 先以公开 HTTP/JSON-RPC、OAuth 和数据库可观察结果形成稳定 `RED_CONFIRMED`；实现完成进入 `READY_FOR_TEST`，再由测试 Agent 独立复测为 `TEST_PASSED`。

## 风险与测试边界

- 测试 Agent 只能依据本契约、MCP-001、APP-011、APP-012 和公开系统设计编写黑盒测试，不读取 `backend/apps/` 或 `backend/config/` 生产实现。
- 必须分别覆盖 OAuth HTTP `401/403`、MCP/JSON-RPC 参数错误、工具业务错误和事务回滚，不能只断言 HTTP 200。
- 必须覆盖新公司、现有公司、多岗位、共享测评/笔试、岗位面试、自定义面试、清空、时区规范化、拒绝终态/保存状态解耦、两个用户隔离及工具白名单。
- 不因客户端缺少邮箱或大模型能力而阻塞；测试直接提供已结构化的公开工具输入。
