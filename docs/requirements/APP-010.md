# APP-010 统一投递业务状态

## 用户需求

投递记录不再把“投递状态”和“面试状态/当前阶段”作为两套业务状态。每个岗位只提供一个可编辑的业务状态，候选展示、个人投递列表、表单、筛选以及共享只读投递展示统一使用以下八项：投递、测评、笔试、一面、二面、其他轮次、HR面、拒绝。

## 规范状态值

接口继续使用 `application_status` 字段，值与展示名固定如下：

| 值 | 展示名 | 说明 |
|---|---|---|
| `applied` | 投递 | 已提交投递，尚未归入其他状态 |
| `assessment` | 测评 | 测评阶段 |
| `written_test` | 笔试 | 笔试阶段 |
| `first_interview` | 一面 | 第一轮面试 |
| `second_interview` | 二面 | 第二轮面试 |
| `other_interview` | 其他轮次 | 三面、复试或其他自定义面试轮次 |
| `hr_interview` | HR面 | HR 面试 |
| `rejected` | 拒绝 | 企业拒绝或流程终止 |

`in_progress`、`offer`、`withdrawn` 不再是新契约允许值。AI 面仍可作为公司共享日程保存，但没有独立的 AI 面业务状态；仅填写或修改日程不会自动改变业务状态。

## 公开契约

- `positions[*].application_status` 是岗位唯一业务状态，创建和 PATCH 只接受上述八个值；缺省为 `applied`。
- 公司聚合对象不维护第二套状态。为兼容已有客户端，若继续返回顶层 `application_status` 或 `current_stage`，二者都必须是主岗位 `application_status` 的只读等值投影，不能由时间或面试记录重新派生，也不能分别写入。
- `/api/v1/applications/` 的 `application_status` 筛选只接受上述八个值，按公司下任一岗位匹配。新前端不再提供独立的当前阶段/面试状态筛选；应用列表的旧 `stage` 参数不再作为业务状态契约，传入时应返回字段级 `400 VALIDATION_ERROR`（日历接口中的事件 `stage` 不受影响）。
- 共享只读投递响应的 `application_status` 和兼容 `current_stage` 使用相同规范值与展示映射，不泄露岗位私有字段。
- 修改阶段日期、清空阶段日期、添加/编辑/删除面试记录均不得隐式修改 `application_status`；修改业务状态也不得清空或改写任何日程字段。

## 历史数据迁移

- `applied`、`rejected` 原值保持。
- `in_progress` 按该岗位已有流程信息映射：测评→`assessment`，笔试→`written_test`，一面→`first_interview`，二面→`second_interview`，三面或自定义面试→`other_interview`，HR 面→`hr_interview`；只有 AI 面或没有可映射流程时归为 `applied`。
- `offer`、`withdrawn` 归为 `rejected`；岗位名称、备注、日程及日程时长保留。实现说明必须记录各旧值的迁移数量。
- 迁移完成后所有公开业务状态只出现规范八值，历史日程仍可供日历、提醒等功能使用。

## 前端行为

- 表单每个岗位只有一个“业务状态”选择器，选项及顺序为：投递、测评、笔试、一面、二面、其他轮次、HR面、拒绝。
- 列表每个岗位只展示一个业务状态标签；不得同时展示“投递状态”和“当前阶段”两个业务状态。
- 状态筛选只使用上述八项；状态同步到 URL 和 API 的字段仍为 `applicationStatus`/`application_status`。
- 状态文案使用本契约中的精确展示名；不得继续显示“已投递”“进行中”“Offer”“已撤回”等旧业务状态。
