# APP-011 修复投递状态下拉与最新流程状态展示

## 任务定位

本需求是对已完成 `APP-010` 的修复/补充任务，不重开 `APP-010`。`APP-010` 已确定的八值枚举、旧值迁移、权限隔离、状态写入原子性和时间/状态不互相写回规则继续有效；本任务仅修订编辑下拉的可观察契约，以及主列表和只读 API 对“最新流程状态”的展示投影。

用户截图反映的可观察问题是：编辑下拉仍出现“已投递/进行中/Offer/已拒绝/已撤回”，主页面状态只能看到“投递/拒绝”，没有随测评、笔试、AI 面或岗位面试进展显示最新流程。该问题必须以公开 UI 和 HTTP API 行为修复，不能通过兼容旧文案掩盖。

## 现状与公开契约依据

- `backend/apps/applications/models.py` 已声明八个规范状态值，但岗位嵌套公开响应当前只返回 `application_status`，未提供岗位级最新流程投影。
- 兼容 flat 响应的 `current_stage` 当前等值于 `application_status`，没有读取公司共享流程或岗位面试记录。
- `frontend/src/components/ApplicationForm.vue` 的业务状态选择器应使用八值选项；`frontend/src/views/ApplicationsView.vue` 当前主列表状态芯片直接展示岗位 `applicationStatus`，无法反映流程记录。
- `APP-010` 的“`current_stage` 与主岗位 `application_status` 等值”仅在本任务涉及的最新流程投影范围内被修订；`application_status` 仍是唯一可编辑、可写入的业务状态字段。

## 规范状态值与展示名

所有新写入、公开返回和前端选项只允许以下八值，并按表中顺序展示：

| 值 | 精确展示名 | 说明 |
|---|---|---|
| `applied` | 投递 | 尚无更具体流程，或用户明确选择投递 |
| `assessment` | 测评 | 公司共享测评流程 |
| `written_test` | 笔试 | 公司共享笔试流程 |
| `first_interview` | 一面 | 第一轮岗位面试 |
| `second_interview` | 二面 | 第二轮岗位面试 |
| `other_interview` | 其他轮次 | 三面、复试、终面或无法归入固定轮次的面试；AI 面的展示映射也使用此值 |
| `hr_interview` | HR面 | HR 面试 |
| `rejected` | 拒绝 | 企业拒绝或流程终止 |

前端和共享展示不得再出现“已投递”“进行中”“Offer”“已拒绝”“已撤回”“流程中”“已录用”“已放弃”等旧业务状态文案。共享申请关系自身的“已拒绝”等关系状态不属于本任务，不应被误改。

## 旧值兼容与迁移

- 新建、POST、PATCH、嵌套岗位写入、flat 兼容写入和应用列表筛选均拒绝 `in_progress`、`offer`、`withdrawn`、`ai_interview`、中文展示名及未知值，并返回字段级 `400 VALIDATION_ERROR`。
- 数据库或历史导入中仍存在旧值时，必须通过迁移或等价的一次性兼容处理归一为八值；不得让旧值进入任何公开响应。
- `applied`、`rejected` 保持不变；`offer`、`withdrawn` 迁移为 `rejected`。
- `in_progress` 按已有可映射流程迁移：测评→`assessment`，笔试→`written_test`，一面→`first_interview`，二面→`second_interview`，三面/复试/自定义岗位面试→`other_interview`，HR 面→`hr_interview`；只有 AI 面或没有可映射流程时→`applied`。岗位、备注、投递时间、共享流程、面试记录和时长必须保留。
- 实现说明必须逐项记录旧值到新值的迁移数量；迁移后重新读取公开 API 时只能看到八值。
- 以上是存量 `application_status` 的迁移规则；运行时最新流程展示对 AI 面的映射见下文，二者不能混淆。

## 最新流程状态派生规则

### 术语和边界

- `application_status`：每个岗位保存的、唯一可编辑的业务状态。表单下拉绑定此字段。
- `current_stage`：只读的“最新流程状态”展示投影，不落库、不接受写入。它服务于主列表、岗位展开行、详情、共享只读响应和兼容 flat 客户端。
- `current_stage` 的值域仍是上述八值；AI 面没有独立值，运行时只把它映射为 `other_interview` 的展示投影。

### 候选流程来源与映射

对某公司下的某个岗位，收集公司级共享流程和该岗位的全部面试记录中 `scheduled_at` 非空的项目：

| 来源 | 条件/名称 | `current_stage` 映射 |
|---|---|---|
| 公司共享流程 | `assessment` | `assessment` |
| 公司共享流程 | `written_test` | `written_test` |
| 公司共享流程 | `ai_interview` | `other_interview`（仅展示投影） |
| 岗位面试 | 规范名称“一面”或等价的 `first_interview` | `first_interview` |
| 岗位面试 | 规范名称“二面”或等价的 `second_interview` | `second_interview` |
| 岗位面试 | 规范名称“HR面”“HR 面”或等价的 `hr_interview` | `hr_interview` |
| 岗位面试 | “三面”“复试”“终面”及其他自定义名称 | `other_interview` |

自定义面试名称只在可明确识别为一面、二面或 HR 面时映射到对应固定值；其余自定义名称统一映射为 `other_interview`。名称映射应忽略首尾空格，并兼容中英文大小写差异；不能因自定义名称未命中而丢弃已有时间。

### 选择优先级

1. `application_status == rejected` 时，`current_stage` 始终为 `rejected`。拒绝是显式终止状态，即使历史日程仍保留也不被日程覆盖。
2. 否则，在上述候选中选择 `scheduled_at` 最新的一项；时间比较使用带时区时间的实际时间点，允许未来已安排的日程参与投影。
3. 候选时间完全相同时，按固定优先级裁决：`hr_interview` > `other_interview` > `second_interview` > `first_interview` > `written_test` > `assessment`。同一映射值仍相同则使用稳定的记录 ID/共享阶段 ID 作为最终平局裁决，不得依赖数据库返回顺序。
4. 没有任何带时间的流程候选时，`current_stage` 回退为该岗位保存的 `application_status`；若历史值已归一，则至少为 `applied`。

因此，主页面显示的是可解释的最新流程投影，而不是永远只显示投递或拒绝；刷新列表、重新打开详情或通过共享只读接口读取时，投影必须保持一致。

## 时间与状态解耦边界

- 新增、修改或清空公司共享测评、笔试、AI 面时间，或新增/编辑/删除岗位面试，只重新计算读取时的 `current_stage`，不得隐式写回、覆盖或迁移 `application_status`，也不得清除或改写其他日程及其时长。
- 显式修改岗位 `application_status` 只修改该岗位保存的业务状态，不新增、删除、改写任何共享流程/面试时间或时长。没有流程时间时，它决定 `current_stage` 的回退值。
- 有流程时间时，主列表和只读 API 可显示由流程派生的 `current_stage`，即使其与保存的 `application_status` 不同；这不是第二个可编辑状态，也不能通过 `current_stage` 写入。
- 修改时间与状态是否导致公司/岗位的 `updated_at` 按既有资源更新语义变化，不作为状态派生依据；不得用更新时间代替流程时间排序。
- 日历、提醒和邮件使用的事件 `stage` 仍按各自公开契约工作；本任务只规定投递状态展示投影，不改事件类型或提醒语义。

## 主页面、表单、筛选和 API 投影

### 表单

- 每个岗位只有一个“业务状态”下拉，选项严格按“投递、测评、笔试、一面、二面、其他轮次、HR面、拒绝”顺序出现。
- 编辑已有岗位时，下拉的值来自 `application_status`；只读的 `current_stage` 不得覆盖下拉值或作为第二个可编辑选择器。
- 保存成功后再次读取详情，保存的 `application_status` 和派生的 `current_stage` 均与上述规则一致；失败时不产生部分写入。

### 主列表与岗位展开

- 公司首岗位行和展开后的每个岗位行均只显示一个“当前流程状态”标签，标签文案来自该岗位 `current_stage` 的精确映射。
- 有测评、笔试、AI 面或岗位面试时间的记录，标签不得退回为“投递”，除非没有流程候选或用户明确状态为 `rejected`；拒绝记录显示“拒绝”。
- 列表刷新、分页、搜索、编辑返回和重新进入页面后，状态标签必须与 API `current_stage` 一致；不得继续直接用旧的 `applicationStatus` 覆盖最新流程投影。
- 其他岗位、共享流程卡和岗位面试时间仍按 APP-009/APP-010 的公开字段展示，状态标签不能重复渲染为“投递状态”加“当前阶段”两套可编辑业务状态。

### 筛选与 URL

- 前端筛选选项只提供八个规范展示名，URL 使用 `applicationStatus`，请求使用 `application_status`。
- `application_status` 筛选按列表可见的 `current_stage` 有效投影匹配，按公司下任一岗位匹配，分页单位仍为公司；这样筛选结果与主列表标签一致。
- 支持既有的单值、逗号分隔值和重复参数规则；非法值、旧值和应用列表的旧 `stage` 参数返回字段级 `400 VALIDATION_ERROR`。日历接口中的 `stage` 参数不受本任务影响。

### HTTP/API 与共享只读响应

- 嵌套公司响应中，每个 `positions[*]` 必须返回保存的 `application_status` 和只读派生的 `current_stage`；二者可不同，但都只能使用八值。
- 顶层兼容 `application_status` 继续表示主/首岗位的保存值；顶层 `current_stage` 表示同一主/首岗位的派生值。顶层不得把其他岗位或公司共享流程错误合并成第二套公司状态。
- POST/PATCH 只接受 `positions[*].application_status` 等保存字段，不接受任何位置的 `current_stage` 写入；成功响应返回重新计算后的投影。
- 共享只读投递接口返回的状态和 `current_stage` 与主岗位的公开投影一致，且不泄露备注、其他岗位私有字段或可写入口。
- 未认证仍为 `401`，不存在/跨用户资源仍为 `404`；状态或流程输入校验失败为 `400 VALIDATION_ERROR`，不得部分修改。

## 可观察验收重点（对应用户截图）

1. 打开编辑表单并展开业务状态下拉的截图中，只能看到八项且顺序为“投递、测评、笔试、一面、二面、其他轮次、HR面、拒绝”；截图中不得出现用户反馈的五个旧文案。
2. 创建或准备含公司共享测评/笔试/AI 面以及岗位一面、二面、HR 面、三面/自定义面试的公开记录，主列表首岗位行、展开岗位行、详情和共享只读响应均显示按时间及平局优先级计算的最新状态，而不是固定“投递”或仅按终态“拒绝”显示。
3. 刷新、翻页、重新打开编辑后，主列表标签与 API `current_stage` 保持一致；显式选择“二面”等八值并保存后，在没有流程时间时不会回退为“投递”。
4. 修改或清空流程时间能改变只读 `current_stage` 投影但不改变保存的 `application_status`、其他时间或时长；修改 `application_status` 也不改写任何流程时间。API 响应和页面行为均可观察验证。

## 风险

- APP-010 已验证的八值写入和迁移行为必须回归；本任务不能借助旧值兼容重新引入旧下拉。
- 同一时间点存在多个来源时必须使用固定优先级，否则不同数据库排序可能产生不稳定截图/API 结果。
- AI 面没有独立状态值，运行时展示映射为 `other_interview`，但存量 `in_progress` 仅 AI 面仍按迁移规则归为 `applied`；测试报告必须分别证明这两个边界。
- 公司级共享流程会被公司下多个岗位共同观察；岗位级面试只能影响所属岗位，不得污染同公司其他岗位的 `current_stage`。
