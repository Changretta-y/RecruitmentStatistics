# APP-012 全局公司库与用户岗位进度关联

## 用户需求

招聘公司按公司实体维护为全局共享库。同一个公司只保留一份招聘网站信息，所有登录用户都可以搜索和复用；用户自己的投递数据仍按用户隔离。用户投递一个公司后，在该公司的折叠菜单下查看和编辑自己的多个岗位进度；新增岗位应直接选择已有公司，不再为每个岗位重复绑定公司或招聘网站。

本需求修复 APP-009/WEB-APP-006 之后的结构缺口：当前 `JobApplication` 既是用户私有的公司聚合又是公司身份，公司名只在单个用户内去重；`application_url` 在顶层和岗位上重复保存；前端公司名为自由文本，建议数据只来自当前用户的投递列表。

## 目标领域模型

### 1. 全局 `Company`

`Company` 属于招聘系统，不属于某个用户；删除用户不得删除公司。建议字段：

| 字段 | 规则 | 说明 |
|---|---|---|
| `id` | 主键 | 全局公司 ID |
| `company_name` | 非空，最长 200 | 对外展示名 |
| `normalized_name` | 非空、全局唯一、服务端生成 | 去首尾空格并按 Unicode 不区分大小写规范化，仅用于去重，默认不对外返回 |
| `recruitment_url` | 可空 URL，最长 500 | 公司唯一招聘网站/招聘查询入口；空值用 JSON `null` |
| `created_at` | 自动写入 | 创建时间 |
| `updated_at` | 自动更新 | 最后修改时间 |

`normalized_name` 是全局唯一键。相同规范化名称无论由哪个用户首次创建，都必须指向同一个 `Company`。公司实体不保存岗位、状态、备注、面试时间或任何用户私有投递信息。

### 2. 用户私有公司投递聚合

沿用 APP-009 的 `JobApplication` 作为“某用户对某公司的投递聚合”，但将 `company_name` 改为指向 `Company` 的非空外键 `company`；`user + company` 全局唯一。`ApplicationPosition`、`SharedStage`、`PositionInterview` 仍挂在该用户的 `JobApplication` 下：

- 一个用户对一个 `Company` 最多一个投递聚合；一个聚合至少一个岗位。
- 多个用户可以分别拥有同一 `Company` 的投递聚合，彼此看不到对方的岗位、备注、状态、面试或共享流程。
- 公司级共享流程的“共享”仍只在同一用户自己的多个岗位之间共享，不表示不同用户共享投递进度。
- 新 API 的招聘网站唯一来源是 `Company.recruitment_url`，岗位不再接受可写的 `application_url`。
- 为兼容旧 flat 客户端，旧 `application_url` 字段可继续作为只读兼容投影；新前端只展示公司级招聘网站一次，不把它当成岗位字段提交。

### 3. 兼容字段与状态

- `company_name`、顶层 `application_url`、八值 `application_status`/只读 `current_stage` 的既有兼容响应继续保留，值从新的公司/首岗位投影，不能因此恢复 APP-010 以前的旧状态值。
- `positions[*]` 的 `application_status` 仍是岗位唯一可写状态；`current_stage` 仍是 APP-011 定义的只读流程投影。
- 新嵌套写入拒绝岗位级 `application_url`；任何 `current_stage`、`user`、`company` 所有者字段和审计时间戳仍不可写。

## 公开 API 契约

所有接口使用 `/api/v1/`、JSON、Bearer Token 和现有统一错误格式。未认证为 `401`；非法输入为 `400 VALIDATION_ERROR`；目标不存在或跨用户私有资源为 `404 NOT_FOUND`。

### 全局公司目录

#### `GET /api/v1/companies/`

受保护的全局公司搜索接口。所有登录用户可读取所有公司，但不能通过此接口读取任何用户的投递数据。

查询参数：

| 参数 | 规则 |
|---|---|
| `search` | 对 `company_name` 做不区分大小写模糊匹配，可空 |
| `page` | 最小 1，默认 1 |
| `page_size` | 允许 10/20/50/100，默认 20，最大 100 |
| `ordering` | 仅允许 `company_name`、`-company_name`、`created_at`、`-created_at`；默认 `company_name,id` 稳定排序 |

响应使用现有分页外形，结果项为：

```json
{
  "id": 7,
  "company_name": "示例科技",
  "recruitment_url": "https://jobs.example.com",
  "created_at": "2026-10-07T08:00:00Z",
  "updated_at": "2026-10-07T08:00:00Z"
}
```

不得返回 `user`、岗位、备注、状态、面试、用户创建关系或其他私有投递字段。

#### `POST /api/v1/companies/`

创建全局公司：

```json
{
  "company_name": "示例科技",
  "recruitment_url": "https://jobs.example.com"
}
```

成功返回 `201 Created` 和完整公司对象。规范化名称已存在时返回 `409 COMPANY_EXISTS`，`details` 至少包含 `company_id` 和现有公司公开对象；不得创建第二行，也不得因重复 POST 静默覆盖已有招聘网站。前端应将该结果转为选择已有公司。公司名和 URL 的首尾空白、空 URL、非法 URL 按字段级错误处理。

#### `GET /api/v1/companies/{company_id}/`

返回全局公司公开对象。公司存在与否不能通过用户投递数据推断。

#### `PATCH /api/v1/companies/{company_id}/`

所有登录用户都可维护共享公司元数据，允许字段仅为 `company_name`、`recruitment_url`。修改后的公司名和招聘网站对所有用户立即可见；UI 必须明确“这是共享信息，会影响所有用户”。规范化名称撞名返回字段级 `400 VALIDATION_ERROR`，失败不改变原公司。未提供字段保持不变，`recruitment_url: null` 清空网站。APP-012 不提供公开删除公司接口；被投递聚合引用的公司不能因用户操作被级联删除。

### 用户投递接口调整

#### `GET /api/v1/applications/`

继续按当前 Token 用户过滤，分页和搜索单位仍是用户的公司投递聚合，而不是全局公司目录。响应新增/保留以下兼容字段：

```json
{
  "id": 27,
  "company_id": 7,
  "company": {
    "id": 7,
    "company_name": "示例科技",
    "recruitment_url": "https://jobs.example.com"
  },
  "company_name": "示例科技",
  "recruitment_url": "https://jobs.example.com",
  "positions": [
    {
      "id": 52,
      "position_name": "后端开发",
      "application_status": "applied",
      "current_stage": "applied",
      "application_time": null,
      "notes": "",
      "interviews": []
    }
  ],
  "shared_stages": [],
  "created_at": "2026-10-07T08:00:00Z",
  "updated_at": "2026-10-07T08:00:00Z"
}
```

列表结果只能包含当前用户自己的 `JobApplication` 和岗位。`company_id` 可用于前端选择/复用；`company`、`company_name`、`recruitment_url` 是公司公开投影。现有 flat 响应所需的 `application_url` 可继续返回公司招聘网站作为只读兼容值，但不得再作为新岗位的独立数据源。

#### `POST /api/v1/applications/`

新客户端必须使用全局公司 ID：

```json
{
  "company_id": 7,
  "positions": [
    {
      "position_name": "后端开发",
      "application_status": "applied",
      "application_time": null,
      "notes": ""
    }
  ],
  "shared_stages": []
}
```

服务端从 `company_id` 绑定公司，不接受前端指定 `user` 或公司名称作为新模型的唯一依据。若当前用户已经有该公司投递聚合，则将不含 ID 的岗位追加到同一聚合并返回完整聚合（保持 APP-009 的 `201` 追加语义），不得新建第二个用户公司聚合，也不得复制招聘网站。一个请求中若带有 `company_id` 与旧 `company_name`，二者不一致返回 `400`。

旧客户端可继续提交 `company_name` 走兼容解析：服务端按全局规范化名称查找/创建 `Company` 后再执行相同的用户聚合逻辑；若同时提交旧 `application_url`，只能在创建新公司且公司 URL 为空时作为一次性迁移输入，不能覆盖已有全局 URL。新嵌套 `positions[*].application_url` 一律拒绝写入。

#### `GET/PATCH/DELETE /api/v1/applications/{id}/` 与岗位/面试子资源

详情、PATCH、删除和 APP-009 的岗位/面试子资源路径保持不变，新增规则如下：

- PATCH 不能更换 `company_id`；公司名称或招聘网站必须通过 `/companies/{company_id}/` 修改。
- 岗位新增/修改/删除继续只影响当前用户、当前公司聚合；省略岗位不删除，删除最后岗位仍返回字段级 `400`。
- 任何 `company_id`、岗位 ID 或面试 ID 的归属校验失败都返回 `404`，不能泄露其他用户是否存在对应投递。
- 公司全局元数据更新不改变任何用户岗位数据；岗位状态/流程更新不改变全局招聘网站。

## 权限与隔离

| 数据 | 读取 | 写入 | 隔离要求 |
|---|---|---|---|
| 全局公司名称/招聘网站 | 任意已认证用户 | 任意已认证用户可 PATCH 共享元数据 | 不含任何投递私有字段；修改对所有用户可见 |
| 用户公司投递聚合 | 仅所属用户 | 仅所属用户 | QuerySet 首先按 `user` 过滤 |
| 岗位、备注、面试、公司级流程 | 仅所属用户 | 仅所属用户 | 通过父聚合 + 当前用户双重归属校验 |
| 共享只读投递 | 按 SHARE-001 授权 | 只读 | 继续使用既有 flat 白名单，不暴露其他岗位私有字段 |

必须验证：用户 A 创建公司和岗位后，用户 B 能在公司目录看到该公司及招聘网站，但不能在应用列表看到 A 的岗位；B 复用该公司创建自己的岗位后，A 仍看不到 B 的岗位。公司网站的公开更新可被双方看到，岗位状态和备注不能互相影响。

## 迁移与兼容

1. 新迁移从当前最新 applications 迁移开始，分阶段建立 `Company`、回填并校验外键，再切换 `JobApplication` 的公司唯一约束为 `user + company`；禁止以空库假设代替存量迁移验证。
2. 从所有现有 `JobApplication.company_name` 按规范化名称生成全局 `Company`；不同用户的同名公司必须合并为一行。展示名采用确定性规则（最早 `created_at`，再按旧记录 ID），实现说明记录合并行数。
3. 从旧顶层和岗位 `application_url` 收集非空 URL，按旧记录创建时间、旧记录 ID、岗位 ID 的固定顺序选择公司 `recruitment_url`。若存在多个不同非空 URL，保留确定性首值，记录冲突数量和候选数量；旧列在兼容窗口内保留为只读历史字段，不得在迁移中静默删除。
4. 现有用户的全部岗位、状态、备注、公司级流程、岗位面试、时长和审计时间戳必须保留；跨用户合并只能合并全局公司身份，不能合并 `JobApplication`。
5. 旧 flat 应用、日历、邮件、共享只读接口继续得到可用的公司名/招聘链接和岗位信息；共享响应继续遵守 SHARE-001 白名单。迁移后不得出现旧状态值，不得因兼容投影泄露 `notes` 或其他岗位数据。
6. 迁移必须可审查：实现说明写明迁移文件、来源/目标计数、公司合并数、URL 冲突数、无法自动处理的异常；对非空数据执行逆迁移或降级操作必须被明确拒绝，不能静默丢失新关系。

## 前端交互契约

1. 新增/编辑共用表单，但公司字段不再是可随意提交的普通文本：使用带搜索的全局公司选择器，展示公司名和招聘网站。选择已有公司后只提交 `company_id`。
2. 当目录没有目标公司时，允许在选择器中创建公司并填写一次招聘网站；创建竞态收到 `409 COMPANY_EXISTS` 时自动转为选择现有公司，不产生重复公司或重复网站绑定。
3. 编辑已有用户公司投递时，已选公司默认锁定；“修改公司招聘网站”调用全局公司 PATCH，并明确这是对所有用户生效的共享修改。修改公司不能把岗位迁移给另一家公司。
4. 岗位表单只维护岗位名、八值业务状态、投递时间、备注和面试流程；移除岗位级招聘网站输入。公司招聘网站在公司标题/折叠菜单中只显示一次，新增多个岗位不得复制该字段。
5. 列表按当前用户的公司投递聚合渲染：公司行显示公司名、招聘网站、岗位数量和展开/折叠控制；展开后显示该用户自己的全部岗位、各自状态和流程，并提供针对岗位的编辑入口。不能因为全局目录存在该公司就显示其他用户岗位。
6. “新增岗位”可从已有公司目录进入，或在现有公司折叠菜单中进入；保存后复用同一 `company_id` 和同一用户公司聚合。刷新、翻页、搜索、重新打开编辑后，折叠状态不应导致岗位数据丢失。
7. 公司目录加载、空结果、网络错误、401、409 重名、400 字段错误和 404 资源不存在均使用现有页面状态模式；失败保存保留输入，不把未保存岗位显示到列表。
8. 前端 API 类型/序列化同时兼容 snake_case 与现有 camelCase；全局目录建议请求必须绑定当前登录用户、取消过期搜索响应，退出登录清理缓存。

## 非范围

- 不开放跨用户共同编辑同一份岗位进度；全局公司共享不等于用户投递共享。
- 不重做 APP-011 八值状态、当前阶段推导、日历/邮件阶段语义或 SHARE-001 授权模型。
- 不在本任务增加公司删除、公司管理员/审核流、收藏、标签、评论、招聘网站抓取或外部同步。
- 不以 UI 截图替代后端迁移、API 权限和原子性证据。

## 验收标准

- [ ] 全局公司目录按规范化公司名唯一；两个用户查询同一公司返回同一 `Company.id`，重复创建返回 `409 COMPANY_EXISTS` 且数据库没有第二行。
- [ ] 已认证用户可搜索/读取其他用户创建的公司公开信息，但目录响应不含岗位、备注、状态、面试、用户 ID 或其他私有字段；未认证访问为 `401`。
- [ ] 用户 A 与用户 B 可分别复用同一公司；两人的用户公司投递聚合、岗位、备注、状态、面试和共享流程完全隔离，跨用户详情/岗位/面试操作为 `404`。
- [ ] 同一用户再次以 `company_id` 新增岗位时复用原用户公司聚合，不新增重复公司、不重复绑定招聘网站，返回结果包含原岗位和新岗位。
- [ ] 公司招聘网站只有全局 `Company.recruitment_url` 一个新写入来源；公司 PATCH 对所有用户可见，岗位状态/备注更新不会改动该 URL；新嵌套岗位提交 `application_url` 被字段级拒绝。
- [ ] 列表和详情按公司折叠展示当前用户自己的多个岗位；每个岗位可独立查看/编辑状态、投递时间、备注和面试流程，折叠/刷新/分页/搜索后数据保持一致。
- [ ] 新增表单必须先选择已有公司或创建一次公司；新增多个岗位不出现重复公司网站输入，创建竞态能复用已存在公司。
- [ ] 存量迁移跨用户合并全局公司但不合并投递；全部岗位及流程数据保留，URL 选择、冲突数、合并数和异常有实现说明，非空数据逆迁移有保护。
- [ ] 旧 flat 应用、日历、邮件、共享只读接口和 APP-011 八值/当前阶段契约回归通过；共享响应不泄露岗位备注或其他用户数据。
- [ ] 测试 Agent 先提交稳定 `RED_CONFIRMED`；功能实现 Agent 仅修改生产实现并提交 `READY_FOR_TEST`；测试 Agent 独立复测提交 `TEST_PASSED`；项目管理 Agent 仅在收到通过报告后验收并设置 `DONE`。

## 风险与测试边界

- 全局公司合并可能触发名称和 URL 冲突；测试必须使用多用户、大小写/空白变体、并发重复创建和多个历史 URL 的存量数据。
- 公司公开元数据与用户私有投递必须分层测试；任何通过全局 Company 查询反查岗位的实现都属于权限缺陷。
- 共享、日历、邮件等旧消费者依赖 `company_name`/`application_url`；实现必须提供兼容投影并执行相邻回归，不能简单删除旧字段。
- 测试 Agent 只通过公开 HTTP API、公开 UI、迁移可观察结果和既有兼容接口测试，不读取或分析 `backend/apps/`、`frontend/src/`；允许写入 `backend/tests/`、`frontend/tests/`、`tests/e2e/`、`docs/test-reports/`。
- 功能实现 Agent 允许写入 `backend/apps/`、`backend/config/`、`backend/manage.py`、`frontend/src/`、`docs/implementation-notes/`，测试目录、任务单、需求契约和质量门槛只读。
- 若需改测试配置或运行时配置，按 AGENTS.md 的归属规则由项目管理 Agent 排定先后；本任务默认不修改共享配置。
