# MCP-001 标准 OAuth MCP 只读服务契约

## 目标

为已登录用户提供一个符合当前 MCP HTTP 授权约定的远程 MCP 服务，使兼容 MCP 的 AI 客户端能够通过 OAuth Authorization Code + PKCE 完成授权，并调用只读工具查询当前用户的投递进度。

本契约以当前项目的 APP-012 公司/岗位聚合 API 为业务数据基线，以 MCP 2026-07-28 协议和官方 Python SDK v2 为主协议基线。SDK v2 的当前说明明确：2026-07-28 主路径取消连接 handshake 和 protocol session；同一 SDK 可兼容 2025-11-25 旧客户端。

- [Python SDK v2 What's New](https://github.com/modelcontextprotocol/python-sdk/blob/main/docs/whats-new.md)
- [Python SDK v2 Authorization](https://github.com/modelcontextprotocol/python-sdk/blob/main/docs/run/authorization.md)
- [Python SDK v2 OAuth Clients/CIMD](https://github.com/modelcontextprotocol/python-sdk/blob/main/docs/client/oauth-clients.md)

实现必须使用官方 Python MCP SDK v2 当前 API（服务端采用 v2 的 `MCPServer`/Streamable HTTP app，客户端验证采用 v2 `Client`/OAuth provider）；不得以 v1 的 `FastMCP` 或手工 `ClientSession.initialize()` 作为主实现方式。具体 SDK 版本、主协议版本和兼容的旧客户端版本必须在实现说明中记录。现代公开测试以 `2026-07-28` 的 `server/discover`/无 protocol session 请求为主；若启用 SDK 提供的旧客户端兼容路径，额外使用 `2025-11-25` 的 `initialize` handshake 回归，但不得把旧 handshake 作为现代请求的前置条件。

## 范围

1. Django OAuth Authorization Server 的 MCP 相关发现文档。
2. OAuth Authorization Code + PKCE（`S256`）公开流程契约。
3. MCP Resource Server 的 Bearer Token 校验和 `/mcp` Streamable HTTP 入口。
4. MCP 2026-07-28 无 handshake 生命周期最小骨架：`server/discover`、`tools/list`、`tools/call`；可兼容 `2025-11-25` 的 `initialize`、`notifications/initialized`。
5. 只读 MCP 工具 `find_applications`。
6. OAuth scope、资源受众、当前用户隔离和必要的 HTTP/JSON-RPC 错误行为。

## 非范围

- 新增投递、修改投递、删除投递、修改测评/笔试/面试时间。
- `preview/apply` 写入确认流、幂等写入、写操作审计。
- 邮箱、聊天记录或附件读取，以及 MCP 服务端调用大模型做信息抽取。
- stdio 服务、旧 HTTP+SSE 兼容端点、MCP Resources/Prompts；旧 2025-11-25 Streamable HTTP handshake 兼容若由 SDK 默认提供则保留，但不扩展为独立旧服务。
- OAuth 管理后台视觉、第三方身份源和多因素认证。

## 公开部署标识

服务通过配置提供以下绝对 URI；测试环境可使用测试域名，不能把生产 URI 硬编码到代码中：

```text
MCP_RESOURCE_URI       = https://<host>/mcp
MCP_AUTHORIZATION_ISSUER = https://<host>
MCP_ENDPOINT           = /mcp
```

`MCP_RESOURCE_URI` 是 OAuth Resource Indicator、Protected Resource Metadata 的 `resource` 和 Token 受众校验使用的规范资源标识。除路径有语义外，统一使用无尾斜杠形式。

## OAuth 发现与授权公开契约

### Protected Resource Metadata

```http
GET /.well-known/oauth-protected-resource/mcp
```

成功返回 `200 application/json`，至少包含：

```json
{
  "resource": "https://<host>/mcp",
  "authorization_servers": ["https://<host>"],
  "scopes_supported": ["applications:read"],
  "bearer_methods_supported": ["header"]
}
```

未携带凭据访问 `/mcp` 或携带无效/过期 Token 时，必须返回 `401`，并在 `WWW-Authenticate` 中以 `resource_metadata` 参数指向上述文档；不得运行 JSON-RPC 方法或业务查询。

### Authorization Server Metadata

```http
GET /.well-known/oauth-authorization-server
```

成功返回 `200 application/json`，至少包含：

```json
{
  "issuer": "https://<host>",
  "authorization_endpoint": "https://<host>/oauth/authorize",
  "token_endpoint": "https://<host>/oauth/token",
  "response_types_supported": ["code"],
  "grant_types_supported": ["authorization_code"],
  "token_endpoint_auth_methods_supported": ["none"],
  "code_challenge_methods_supported": ["S256"],
  "scopes_supported": ["applications:read"],
  "client_id_metadata_document_supported": true
}
```

2026-07-28 主路径采用 Client ID Metadata Documents（CIMD）：客户端将稳定的 HTTPS metadata URL 直接作为 `client_id`，Authorization Server 获取并校验该 JSON 文档，不创建固定的客户端密钥。Authorization Server Metadata 必须声明 `client_id_metadata_document_supported=true`。

动态客户端注册（DCR）仅作为 2025-11-25 或其他旧客户端的兼容能力，不是本任务的必需能力；如果实现提供 `POST /oauth/register`，必须在实现说明中注明它是兼容入口，并继续执行公共客户端、精确 redirect URI 和 PKCE `S256` 校验。现代客户端不应因 DCR 未开放而无法通过 CIMD 完成授权。

### Authorization Code + PKCE

```http
GET /oauth/authorize
```

授权请求必须支持并校验：

- `response_type=code`
- `client_id`：现代客户端为 CIMD HTTPS metadata URL；兼容旧客户端时可为 DCR 返回的 client ID
- `redirect_uri`：必须与客户端注册值精确匹配
- `scope`：只能请求 `applications:read`
- `state`：原样带回，客户端负责校验
- `code_challenge`
- `code_challenge_method=S256`
- `resource=https://<host>/mcp`

用户未登录时进入现有账户登录边界；登录后必须显示本次客户端将获得的读取权限并由用户同意。授权成功只通过精确匹配的 `redirect_uri` 返回一次性、短时效 authorization code 和原样 `state`；应带回当前 issuer 的 `iss`，供 SDK v2 客户端执行 authorization-server mix-up 校验；不得在重定向 URI 中返回 Access Token。

授权码交换：

```http
POST /oauth/token
Content-Type: application/x-www-form-urlencoded
```

请求至少包含：

```text
grant_type=authorization_code
code=<authorization-code>
client_id=<client-id>
redirect_uri=<same-redirect-uri>
code_verifier=<pkce-verifier>
resource=https://<host>/mcp
```

成功返回 OAuth Token 响应，至少包含 `access_token`、`token_type=Bearer`、`expires_in`、`scope=applications:read`；可返回 `refresh_token`，如返回则必须轮换并失效旧 Refresh Token。Access Token 必须绑定当前用户、客户端和 `MCP_RESOURCE_URI`，MCP Resource Server 必须验证资源受众。

以下情况必须拒绝且不得签发 Token：缺失或不支持 PKCE、`code_verifier` 不匹配、授权码重复使用/过期、redirect URI 不匹配、resource 不匹配、scope 超出授权范围、客户端不存在或被禁用。错误使用 OAuth 标准错误名，不能泄露用户是否存在或授权码内容。

## MCP Streamable HTTP 契约

### 入口和认证

```http
POST /mcp
Authorization: Bearer <access-token>
Accept: application/json, text/event-stream
Content-Type: application/json
```

- 服务只提供一个 MCP endpoint：`/mcp`。
- 每个 HTTP 请求都必须携带 Bearer Token；Token 不得出现在 URL 查询参数。
- 服务以 stateless/no protocol session 为主，不依赖进程内存保存用户、授权或查询状态；2026-07-28 现代请求不返回也不要求 `Mcp-Session-Id`。官方 SDK v2 的旧客户端兼容路径可按 `2025-11-25` 需要处理 handshake/session，但不能让现代请求依赖该状态。
- POST 请求中的 JSON-RPC 请求返回 `application/json` 结果即可；通知/响应被接受时返回 `202` 空响应。
- 本任务不提供服务端主动推送和订阅；现代客户端不要求旧的独立 GET/SSE listen 流。对不支持的旧 listen 请求返回 `405 Method Not Allowed` 是可接受行为。
- 必须校验 `Origin`，拒绝不在允许列表内的来源，避免 DNS rebinding。

### 生命周期与能力

现代 2026-07-28 客户端通过普通 MCP 请求完成 `server/discover`；协议版本、客户端能力和必要的 client info 位于请求 `_meta`，不要求先发送 `initialize` 或 `notifications/initialized`。随后通过 `tools/list` 发现工具、通过 `tools/call` 调用工具。官方 Python SDK v2 `Client` 应作为客户端验证主路径。

如服务启用 2025-11-25 兼容路径，旧客户端可以先发送 `initialize` 和 `notifications/initialized`，服务端按该版本规则响应；这只是兼容回归，不得成为 2026-07-28 主路径的验收前置条件。

`tools/list` 必须返回 `find_applications` 的名称、用途描述、完整 JSON Schema；服务端不声明未实现的 prompts/resources 能力。

未知方法或工具名、协议版本不可用、JSON-RPC 结构错误使用 JSON-RPC 错误；认证错误使用 HTTP `401/403`，不得伪装成工具成功结果。

## `find_applications` 工具契约

### 工具定义

```text
name: find_applications
title: 查询我的投递进度
scope: applications:read
annotations.readOnlyHint: true
```

输入为 JSON object，所有字段可选，但至少应允许以下定位和筛选字段：

```json
{
  "application_id": 123,
  "company_name": "腾讯",
  "position_name": "后端开发",
  "search": "后端",
  "application_status": "in_progress",
  "stage": "written_test",
  "page": 1,
  "page_size": 20
}
```

规则：

- `application_id`、`company_name`、`position_name`、`search` 遵循 APP-012 当前公开语义；服务端负责去除名称首尾空白。
- `application_status` 只接受当前项目公开状态枚举；`stage` 只接受当前阶段筛选值。
- `page` 最小为 1，`page_size` 只能为 10/20/50/100，默认 20。
- 不接受 `user_id`、任意数据库字段名、SQL、REST URL 或任意排序表达式作为查询条件。
- 查询结果只来自 OAuth Token 对应用户；不能通过输入参数改变数据归属。
- 工具不创建、修改或删除任何数据。

### 成功结果

工具结果应同时提供 MCP `content` 中的可读摘要和 `structuredContent`，结构遵循 APP-012 的公司聚合公开响应，至少包含：

```json
{
  "count": 1,
  "page": 1,
  "page_size": 20,
  "total_pages": 1,
  "results": [
    {
      "id": 123,
      "company_id": 9,
      "company": {"id": 9, "company_name": "腾讯", "recruitment_url": null},
      "company_name": "腾讯",
      "recruitment_url": null,
      "application_status": "in_progress",
      "current_stage": "written_test",
      "shared_stages": [],
      "positions": []
    }
  ]
}
```

真实结果必须包含当前公开 API 已定义的完整公司/岗位/共享流程/面试字段，不得为了 MCP 另造一套数据模型。无匹配时返回成功的空分页结果，不泄露其他用户是否存在匹配记录。

### 错误行为

- 无 Token、Token 无效、过期或受众不匹配：HTTP `401`，带 `WWW-Authenticate`。
- Token 有效但缺少 `applications:read`：HTTP `403`，错误为 `insufficient_scope`。
- 工具参数不符合 schema：JSON-RPC 参数错误或工具执行错误，明确指出字段问题，不执行查询。
- 业务查询异常：工具结果 `isError=true`，不得返回堆栈、Token、密码或跨用户数据。

## 验收口径

1. 未认证 MCP 请求能通过 Protected Resource Metadata 和 `WWW-Authenticate` 找到授权服务器；Authorization Server Metadata 声明 CIMD 支持，endpoint、scope、PKCE 能力与实际服务一致；DCR 不属于必需验收项。
2. 现代客户端使用 CIMD `client_id` 完成 Authorization Code + PKCE `S256` + `resource=/mcp` 流程，可签发只允许访问本 MCP 资源的 Bearer Token；非法 verifier、redirect URI、resource、重复 code 均稳定拒绝。
3. 现代 `2026-07-28` 客户端不经过 `initialize` 即可完成 `server/discover`、工具发现和 `find_applications` 调用；如启用旧客户端兼容，`2025-11-25` handshake 也能完成同一只读查询。
4. 工具结果遵循 MCP Tools 结构和 APP-012 公司聚合结构；两个用户分别调用同一工具时只能看到自己的公司、岗位、共享阶段和面试数据。
5. 本任务实现不包含任何写工具；`tools/list` 不暴露新增、修改、删除或阶段更新时间工具，`find_applications` 调用不改变数据库。
6. stateless/no protocol session、OAuth 认证、协议错误、工具参数错误和空结果均可由公开 HTTP/JSON-RPC 输入输出判定；测试先形成稳定 RED，再由实现 Agent 修复并接受独立复测。

## 风险与后续任务

- 现有网页登录使用项目 JWT，不等于 OAuth Authorization Server；实现需要明确浏览器授权与 Django 用户会话的衔接，不能直接把网页 Refresh Token 当 MCP Token。
- 现有 APP-012 业务数据已经是公司聚合结构，MCP 不能回退到 APP-009 的单条 flat 记录语义。
- CIMD 是本任务的现代主路径；DCR 仅为旧客户端兼容选项，不得反向要求现代客户端必须注册。Refresh Token 轮换和 OAuth 管理页面不在本任务的最小验收中，但不能以固定长期 Token 替代 PKCE、资源受众和用户隔离。
- SDK v2 的现代无 handshake/no protocol session 与 2025-11-25 旧 handshake/session 是两条协议时代路径；测试和实现说明必须明确区分，不能用旧 initialize 测试代替现代主路径证据。
- 写入工具、预览确认、幂等和审计另行拆分，不因本任务服务骨架完成而提前开放。
