# WEB-APP-008 主页面公司建议、拒绝末位排序与页码导航

## 任务定位

- 状态：`PLANNED`
- 用户需求：主页面关键字输入框在点击/聚焦时展示当前用户已经投递过的公司；选择公司后填入关键字并执行搜索。投递列表默认将拒绝公司放到最后，并提供可选择页码或可输入页码跳转。
- 用户价值：用户可以从自己的历史投递快速开始搜索；默认列表先看到仍在推进中的公司；大量投递记录可以直接定位到目标页，不必逐页点击“下一页”。
- 依赖：`APP-009` 公司聚合与嵌套岗位公开 API、`APP-010` 八值状态与筛选契约、`APP-011` 岗位级 `current_stage` 投影、`WEB-APP-006`/`WEB-APP-007` 主页面公司聚合与列表查询状态。
- 现状依据：现有主页面调用 `GET /api/v1/applications/`，HTTP 查询参数为 `page`、`page_size`、`search`、`application_status`、日期筛选和 `ordering`；前端 URL 状态使用 `page`、`pageSize`（兼容 `page_size`）、`search`、`applicationStatus`、日期筛选和 `ordering`。分页当前只有上一页/下一页。

本需求只增加主页面可观察行为，不改变投递状态八值、共享授权、共享只读 API 或应用列表的用户隔离模型。

## 公司建议数据来源与权限边界

1. 公司建议复用当前用户认证后的 `GET /api/v1/applications/`，不新增全局公司搜索接口，也不得从 `GET /api/v1/sharing/users/{user_id}/applications/`、其他用户数据、浏览器扩展数据或未授权缓存读取建议。
2. 输入框首次获得焦点或被点击时，前端在独立的建议状态中读取该用户的完整投递列表：使用现有 `page_size=100`，从 `page=1` 读取至响应 `total_pages`，不带 `search`、`application_status`、日期筛选；使用默认列表排序以获得稳定的最近更新顺序。建议加载不得替换主列表数据、URL 或主列表的 `page`。
3. 建议只提取每个公司聚合对象的公开 `company_name`（前端映射后的 `companyName`）；下拉菜单不得展示或通过建议接口新增暴露岗位、备注、链接、状态、日程、用户 ID 或其他字段。公司名按去除首尾空白后的不区分大小写键去重，保留首次出现的公开文案。
4. 建议缓存必须绑定当前认证用户；退出登录、用户切换或收到 `401` 时清除建议缓存。建议请求失败只显示可重试的建议错误，不得阻止用户继续手工输入和执行普通列表搜索。
5. 该数据源天然继承应用列表的 `IsAuthenticated` 和 `QuerySet` 当前用户过滤：用户 A 的建议不得出现用户 B 仅拥有或共享给用户 A 之外的公司；未认证不得通过建议请求得到任何公司名。建议列表为空时显示空状态，不伪造公共公司名。

## 公开 API 契约

### 1. 应用列表响应与默认排序

入口保持：

```http
GET /api/v1/applications/
```

响应字段、分页结构、搜索和筛选语义保持 APP-009/APP-010/APP-011；不得新增客户端可写的排序字段，也不得返回内部排序标记。默认排序仅调整顺序：

1. 先计算公司拒绝分组 `rejected_bucket`，该字段只在服务端内部使用，不出现在响应中。
2. `rejected_bucket=0` 为非拒绝公司，`rejected_bucket=1` 为拒绝公司。
3. 同一分组内按现有默认 `updated_at DESC, id DESC` 稳定排序。

前端当前默认会发送 `ordering=-updated_at`；请求未提供 `ordering` 或明确使用该默认值时，均必须执行上述拒绝分组排序。这样服务端排序先于分页，跨页不会出现后续页仍有非拒绝公司而前页已被拒绝公司占满的错误。

公司拒绝分组规则：

- 对有岗位的公司，使用 APP-011 的岗位级有效 `current_stage`；若兼容数据缺少投影，则回退同一岗位的 `application_status`。只有公司下所有公开岗位的有效状态均为 `rejected` 时，才归入拒绝分组。
- 对无岗位的兼容 flat 公司，使用顶层 `current_stage`，缺失时使用顶层 `application_status`。
- 多岗位公司只要有一个公开岗位不是拒绝，就归入非拒绝分组；不得因某个已拒绝岗位把仍有进行中岗位的公司排到最后。
- `current_stage` 的计算、`application_status` 筛选匹配、共享流程映射和拒绝优先规则继续以 APP-011 为准；本需求不重新定义状态。

显式选择其他合法 `ordering` 时，按用户选择的字段排序，并以 `id DESC` 稳定裁决；不额外强制拒绝末位，以保留现有排序功能。非法排序仍返回字段级 `400 VALIDATION_ERROR`。

### 2. 查询参数与错误行为

| 参数 | 合法行为 |
|---|---|
| `page` | 正整数，默认 `1`；`0`、负数、非整数、空值或小数返回 `400 VALIDATION_ERROR`，详情指向 `page`。大于 `total_pages` 时沿用现有公开行为：`200`、结果为空、`count/total_pages` 保持真实值，并提供指向最后有效页的 `previous`。无数据时 `total_pages=0`。 |
| `page_size` | 只接受 `10/20/50/100`，默认 `20`；非法值仍返回字段级 `400 VALIDATION_ERROR`，详情指向 `page_size`。 |
| `search` | 继续按公司名或岗位名模糊匹配，只作用于当前用户数据。 |
| `application_status` | 继续按 APP-010/APP-011 八值和有效 `current_stage`，按公司下任一岗位匹配；不改变其单值、逗号分隔、重复参数规则。 |
| `ordering` | 继续使用现有白名单；缺省或 `-updated_at` 执行拒绝分组默认排序。 |

成功响应继续提供 `count`、`page`、`page_size`、`total_pages`、`next`、`previous`、`results`。排序必须发生在分页之前，且 `next`/`previous` 链接保留所有原查询参数，包括 `page_size`、搜索、筛选和排序。

### 3. 建议请求的失败隔离

建议请求使用与主列表相同的认证凭据和公开应用列表权限。建议请求的 `401` 只能触发登录态失效处理或隐藏建议，不得回退到未认证接口；建议请求的网络/服务错误不改变当前主列表，也不改变 URL 查询状态。

## 前端 UI 与查询状态契约

### 1. 公司建议

- 关键字输入框保留现有名称、`search` URL/API 参数、Enter 和“查询”按钮行为。
- 输入框获得焦点或被点击时打开建议面板；已缓存建议可立即显示，首次打开显示加载状态后填充。输入已有文字时，建议按不区分大小写的包含匹配过滤；输入为空时显示当前用户的去重公司列表。
- 建议面板是可观察、可访问的列表框：输入框承担 combobox 语义，建议项可被键盘/鼠标聚焦和选择，建议项文本为公司名，不显示其他投递字段。无匹配显示“没有匹配的历史公司”；加载失败提供重试，不隐藏输入框。
- 点击建议项后，输入框填入该项的规范公司名，关闭建议面板，并调用现有搜索提交流程一次：`page` 重置为 `1`，`search` 使用该公司名，`page_size`、状态筛选、日期筛选和 `ordering` 保持当前值；URL 和随后 `/api/v1/applications/` 请求同步更新。普通输入、Enter、查询、重置的既有语义保持。
- 打开/关闭、输入过滤和选择建议不发起任何写请求，不改变状态筛选、日期筛选或排序；建议读取可以是多次 GET，但不得将建议分页请求误显示为主列表结果。

### 2. 拒绝末位展示

- 主列表按 API 返回顺序展示；前端不得只对当前页本地排序，也不得根据旧的 `application_status` 覆盖 APP-011 的 `current_stage`。
- 单岗位拒绝公司排在非拒绝公司之后。多岗位公司遵循 API 的“全部岗位拒绝才归末位”规则。
- 用户选择除默认 `最近更新` 外的合法排序时，列表只按该排序及服务端稳定 tie-break 展示。

### 3. 页码选择与跳转

- 保留上一页、下一页，并增加可选择页码控件（页码选项为 `1..total_pages`）和可输入页码跳转控件；页码控件必须带当前页、总页数和可访问名称。`total_pages=0` 时当前页固定展示为 `1`，页码选择与跳转控件禁用。
- 选择页码或提交合法输入时，只改变 `page`，保留 `page_size`、`search`、状态筛选、日期筛选和 `ordering`；请求仍使用 HTTP `page/page_size`，主页面 URL 继续兼容既有 `pageSize` 与 `page_size` 解析，并按当前序列化契约写回。
- 合法页码为无前导语义问题的十进制正整数且范围为 `1..total_pages`。空白、空值、`0`、负数、小数、指数形式、非数字、超出最大页或超过安全整数均视为非法；显示字段级 UI 错误，不发起列表请求，不清除任何查询条件。
- 页码选择/输入不能跨越边界：第一页“上一页”禁用，最后一页“下一页”禁用。筛选、搜索、日期条件、排序或 `page_size` 改变时按现有契约把 `page` 重置为 `1`；仅翻页时不重置其他条件。
- 从外部 URL 进入且 `page` 为正整数但超过服务端返回的 `total_pages` 时，前端将其规范化为最后有效页；无数据时规范化为 `1`。规范化只改 `page`，保留其余 URL/API 查询条件，不进入重复重定向循环。
- API 直接收到非法 `page` 仍按本需求的字段级 `400` 契约处理；UI 本地拦截非法页码不替代 API 对其他客户端的校验。

## 非范围

- 不改变 APP-010/APP-011 的状态值、投影、迁移、筛选匹配或共享只读字段。
- 不把公司名建议扩展为全站公司目录、其他用户公司搜索、共享联系人搜索或公共推荐；不改变共享授权。
- 不新增编辑、删除、批量操作、排序字段、页面尺寸选项或移动端视觉重设计。
- 不改变日历/邮件内部 `stage` 语义，不改变应用列表分页单位（仍为公司聚合对象）。

## 可观察验收重点

1. 当前用户有跨多个 `page_size=100` 页的公司记录时，聚焦输入框可看到所有去重公司名；另一个用户同名但未属于当前用户的公司不出现，建议请求只观察到当前用户的认证列表。
2. 点击建议公司后输入值、URL 的 `search` 和列表请求一致，其他查询状态不丢失，且只发起一次主搜索；手工输入和 Enter 仍可搜索。
3. 默认列表在服务端分页前把非拒绝公司排在前、完全拒绝公司排在后；多岗位公司仅在所有岗位均拒绝时进入末位分组；显式自定义排序仍生效。
4. 页码选择和合法手工跳转可到任一页；非法/越界输入不发请求且保留查询状态；分页请求携带既有 `page_size`、筛选、搜索和排序状态。
5. 未认证、跨用户、建议加载失败、空数据、最后一页和 API 非法参数均有公开可观察结果，且不泄露其他用户数据。
